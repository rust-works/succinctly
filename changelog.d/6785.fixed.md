- **yq: a write through a member a `<<` merge brought in changes the source's node, as in yq** (#6785). With `a: &a {x: 1, z: 9}`, `b: &b {y: 2, z: 8}` and `item: {<<: [*a, *b], k: 0}`, `.item.x = 5` set only `item`'s copy of `x` and left `a.x` at `1`; yq sets `a.x`, so every mapping that merges `a` shows `5`. `.item.x |= . + 1`, `del(.item.x)`, `.item[] |= 7` and `setpath` do the same, a key two sources hold is written in the last one (`.item.z = 7` sets `b.z`) while the mapping keeps showing the first (`item.z` stays `9`), and the reverse direction now holds too: `.a.x = 5` and `del(.a.x)` change `item`. Writes through an own key (`.item.k = 7`) and a mapping a write replaced (`.item = {"q": 1} | .item.x = 5`) are unchanged. A write whose body runs on the merging mapping with a path of its own (`.list[] |= (.x = 7)`, `with(.item; .x = 4)`) still changes only the mapping's copy. A source removed whole (`del(.a)`) leaves the members it merged, a key the first of three sources loses shows through from the second, and a mapping that is itself aliased passes the new value on to its alias slots. Checked against yq v4.53.3 over 44 rows in five documents, every one a match (`tests/yq_cli/i6785.rs`), and a write that changes all 4,000 members of a document takes 0.4s in a debug build, linear in the number of merges.
