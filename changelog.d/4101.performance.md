- **jq: a position read before the element the slot scan last found steps back to it instead of rescanning from the first element** (#4101). `[range(length-1;-1;-1) as $i | getpath([$i]) | tostring | key | 0] | length` visited n(n+1)/2 elements in the scan that finds an element in its parent (8,002,528 at n = 4,000, against 1,089 for the same reads in ascending order). The scan now walks back from the remembered element (`DocumentCursor::prev_element`, `prev_sibling` for JSON) when the node ids put the read within 256 elements behind it, and takes the parent of such a position from the remembered extent rather than `enclose`; a read further back (near the start, or a stride past 256) is not attempted and costs what it cost before. Interleaved A/B, output identical on every row: descending reads of 16,000/32,000/64,000 elements read -50.7%/-50.8%/-51.4% on an M4 Pro (1.82 s to 0.90 s, 7.18 s to 3.53 s, 28.8 s to 14.0 s) and -51.2%/-51.9%/-51.8% on a Ryzen 9 7950X, which is the same query read in ascending order (13.92 s against 13.97 s at 64,000 on the M4 Pro). The first-and-last zig-zag and two interleaved distant fan-outs read -2.2% to -3.9% and -0.1% to -3.0% on both chips, and ascending reads -0.8% to +0.2%. The in-order and non-fan-out rows (`.`, an in-order and a skipping fan-out over 100,000 elements, a 300 x 300 matrix, `paths` over 20,000 records) are inside the A/A control's range on both chips, with retired instructions -0.16% to +0.14% (M4 Pro) and -0.02% to +0.11% (7950X, cachegrind). These queries stay quadratic: each `.[$i]` read in a path context is itself an O(i) sibling walk, which this does not touch. YAML and a mapping's members keep the scan from the first element.
