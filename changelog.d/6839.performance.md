- **yq: an update over a list of merging mappings or aliases is linear, not quadratic** (#6839). `.list[] |= (.x = 7)` over N mappings that each merge one source (`<<: *base`), or N aliases of it (`- *base`), took time that grew about fourfold per doubling of N: each nested write walked the whole table of merged members and aliases, whose paths are the document's and not the body's, each path prefix looked for its anchor among every alias, and the propagation after the write rebuilt the document around each alias slot. The table is now off inside an update body with a target below the root, alias positions are found through a hash, and a slot is replaced in place. Release builds, interleaved A/B, output identical on every row (`ab-cli.py`, 5 repetitions, medians): on a 7950X the merge rows at 2,000/4,000/8,000 mappings read 505/1,945/8,429 ms before and 28/56/115 ms after, the alias rows at 4,000/8,000/16,000 read 577/2,289/9,027 ms before and 20/39/78 ms after; on an M4 Pro 277/1,058/4,166 ms before and 22/41/81 ms after for the merge rows, 386/1,496/5,909 ms before and 16/29/55 ms after for the aliases. After, the time doubles with N out to 64,000 mappings (1.06 s on the 7950X) and 32,000 aliases (155 ms). A document with no aliases or merges is unchanged on the M4 Pro (-0.3% median over three update rows); on the 7950X its update rows read +1.2%, and so do read-only rows that never touch this code (`.items | length`, `select`), which is the binary's layout and not this change.
