- **jq / yq: a body rebuilt for each value that reads its variable keeps the tails after its last reading stage, so the stages after it are linear in the pipe's length** (#5436).
  #5424 linked a pipe that a variable substitution rebuilds to the kept tails of the pipe it was rebuilt from, but only
  when the pipe reads no variable; a body that reads its variable (`. as $x | (. + $x | ...)`, a `reduce` or `foreach`
  update that mentions `$i`) still copied its rest per value per stage. A stage that reads no variable is the same in
  every rebuild, so a pipe that reads one now has a table of its own for the pipes rebuilt from it, whose runs end at a
  reading stage. A tail that starts at or before the last reading stage is copied for the value as before, and the copy
  reaches the same table at its offset, so the tails after the variable are kept however the copy was reached. The
  tails kept hold no variable: they are plain pipes, never split behind `Shared` nodes, so a container keeps its storage
  identity (`[nan] as $a | ... | . == $a`) and the owned front doors still see the stages. A variable read in the last
  stage leaves no tail to keep and is unchanged. 20,000 values, interleaved min of 7 CPU seconds, output identical:
  `[range(0;20000) | . as $x | (. + $x | . + 1 | ... x n)] | length` n=6 0.069 s -> 0.042 s, n=14 0.357 s -> 0.121 s,
  n=40 2.221 s -> 0.379 s on an AMD Ryzen 9 7950X (the same pipe reading no variable: 0.380 s); n=6 0.056 s -> 0.034 s,
  n=14 0.219 s -> 0.086 s, n=40 1.358 s -> 0.258 s on an Apple M4 Pro (reading none: 0.261 s). The `reduce` update
  (2.018 s -> 0.441 s, 1.254 s -> 0.331 s) and the `foreach` extract (2.025 s -> 0.442 s, 1.244 s -> 0.335 s) match it,
  and a variable read in the middle of a 40-stage pipe is 20-22% faster on both. A variable read in the last stage, in
  every stage, and a pipe that reads none are within 3% on both machines (the noise of the control).
