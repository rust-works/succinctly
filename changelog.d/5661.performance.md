- **jq: `-n` with `input`/`inputs` converts each document when the program reads it, not all of them up front** (#5661). `first(inputs)` over a 56 MB NDJSON file parsed and held all 1.6 million documents before the filter ran (1.7 s, 952 MB peak, jq 4 ms and 2.5 MB). A clean single-source plain-JSON stream (strict JSON `serde_json` accepts, no BOM, documents nested no deeper than 64) now queues each document's byte range and converts it, and counts its line, on the read that pops it, so a program that stops early (`first(inputs)`, `limit(n; inputs)`, `input` in a counted loop) converts only what it reads and holds the text and those ranges: on the 56 MB file `first(inputs)` takes 0.36 s and 205 MB (was 4.0 s and 952 MB), and on a 7 MB file 57 ms (was 428 ms), measured on an Apple M5 Max (interleaved min of 5, a loaded box, so read the ratios). A program that reads every document costs what it did. A stream with a parse error, a BOM, a number only jq reads, several files, `-s`, `--stream`, `--seq` or `-R` keeps the up-front route and its error placement; jq 1.7.1 agrees on 2,624 stream-by-program rows.
That route also no longer makes two more whole-stream passes before the filter runs: the end-of-stream marker (#4303) is read off the document ranges it already found instead of a strict re-scan, and each document's line is counted when it is read, with nothing kept per unread document. On an AMD Ryzen 9 7950X (interleaved min of 7, a loaded box) `first(inputs)` on a 77 MB NDJSON file takes 229 ms and 117 MB (was 578 ms and 194 MB) and on 9.7 MB 35 ms (was 79 ms), and `reduce inputs` is 5-7% faster with a third less peak memory.
