- **jq: `-n` with `input`/`inputs` converts each document when the program reads it, not all of them up front** (#5661). `first(inputs)` over a 56 MB NDJSON file parsed and held all 1.6 million documents before the filter ran (1.7 s, 952 MB peak, jq 4 ms and 2.5 MB). A clean single-source plain-JSON stream (strict JSON `serde_json` accepts, no BOM, documents nested no deeper than 64) now queues each document's byte range and converts it, and counts its line, on the read that pops it, so a program that stops early (`first(inputs)`, `limit(n; inputs)`, `input` in a counted loop) converts only what it reads and holds the text and those ranges: on the 56 MB file `first(inputs)` takes 0.36 s and 205 MB (was 4.0 s and 952 MB), and on a 7 MB file 57 ms (was 428 ms), measured on an Apple M5 Max (interleaved min of 5, a loaded box, so read the ratios). A program that reads every document costs what it did. A stream with a parse error, a BOM, a number only jq reads, several files, `-s`, `--stream`, `--seq` or `-R` keeps the up-front route and its error placement; jq 1.7.1 agrees on 2,624 stream-by-program rows.
That route also no longer makes two more whole-stream passes before the filter runs: the end-of-stream marker (#4303) is read off the document ranges it already found instead of a strict re-scan, and each document's line is counted when it is read, with nothing kept per unread document. On an AMD Ryzen 9 7950X (interleaved min of 7, a loaded box) `first(inputs)` on a 77 MB NDJSON file takes 229 ms and 117 MB (was 578 ms and 194 MB) and on 9.7 MB 35 ms (was 79 ms), and `reduce inputs` is 5-7% faster with a third less peak memory.
On an Apple M4 Pro (interleaved min of 7) the same change takes `first(inputs)` on a 63 MB NDJSON file to 125 ms and 104 MB (was 286 ms and 204 MB) and on 7.9 MB to 19 ms (was 38 ms), and programs that read every document are 9-10% faster with peak memory halved.
The same route (#5854) now builds one index per run of consecutive documents (16 KiB of text for the first run, doubling to 1 MiB) and converts each document from its root in that index, instead of building and dropping an index for every document. `reduce inputs`, `last(inputs)` and the like over an NDJSON file of small records are 13.5-15.8% faster on an AMD Ryzen 9 7950X and 7.2-8.6% faster on an Apple M4 Pro (interleaved min of 11, 8 MB and 64 MB; 0 output differences; peak memory unchanged), and `first(inputs)` is unchanged within noise (+0.6% to +1.7% on the 7950X, -0.6% to +0.4% on the M4 Pro) because its first run is small.
A program that reads `input`/`inputs` without `-n` takes the same route (#5855), since its driver loop already pops its documents from the queue the program's own `input` draws from, and the strict end-of-stream scan is skipped for it as well. `jq -c '[., input_line_number] | halt'` on a 64 MB NDJSON file takes 0.12 s (was 0.82 s) on an Apple M4 Pro and 0.12 s (was 1.41 s) on an AMD Ryzen 9 7950X, and a program that reads every document is 4-8% faster on the M4 Pro (`[., input] | length` 1.37 s against 1.46 s) and 19-36% faster on the 7950X (`[., input] | length` 1.66 s against 2.60 s, `input_line_number` 2.31 s against 3.20 s); interleaved min of 7, output identical, and the same programs under `-n` do not move. A stream the route turns down, `-s`, `--stream` and several files keep the up-front route. None of 4,840 rows (22 programs, 22 streams, 5 flag sets, a file and stdin) answers differently from the build before the change, and 1,622 rows that jq 1.7.1 answers the same are pinned.
A stream that turns malformed after a clean start keeps that start lazy too (#5853), with or without `-n`: the documents before the first fault are converted when read, and the eager route reads the stream from there, with the fault's error placement, the documents jq reads after resuming, and the number or literal the fault's own byte completes left to it (`1 2 3}` still gives `1 2` and then the error). One trailing `}` or `nan` used to send the whole stream down the eager route. On an Apple M4 Pro (interleaved min of 7) `first(inputs)` on a 63 MB NDJSON file with a trailing `}` takes 230 ms and 129 MB (was 2.71 s and 897 MB), and on 7.9 MB 32 ms and 24 MB (was 341 ms and 117 MB). On an AMD Ryzen 9 7950X it takes 250 ms and 133 MB (was 4.08 s and 1.08 GB), and on 7.9 MB 32 ms and 24 MB (was 565 ms and 144 MB). A fault in the middle of the stream pays for the eager read of what follows it (95 ms on the M4 Pro, was 245 ms; 148 ms on the 7950X, was 385 ms), `try inputs` over a stream with a trailing `}` takes 155 ms (was 355 ms) and 173 ms (was 584 ms), and a fault within the first few documents and clean streams are unchanged (0.94-1.01x; the early-fault row holds 8-13 MB more at peak). jq 1.7.1 agrees on 43,560 stream-by-program rows with a fault of 11 kinds after 1 to 3 documents.
