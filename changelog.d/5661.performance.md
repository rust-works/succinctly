- **jq: `-n` with `input`/`inputs` converts each document when the program reads it, not all of them up front** (#5661). `first(inputs)` over a 56 MB NDJSON file parsed and held all 1.6 million documents before the filter ran (1.7 s, 952 MB peak, jq 4 ms and 2.5 MB). A clean single-source plain-JSON stream (strict JSON `serde_json` accepts, no BOM, documents nested no deeper than 64) now queues each document's byte range and converts it, and counts its line, on the read that pops it, so a program that stops early (`first(inputs)`, `limit(n; inputs)`, `input` in a counted loop) converts only what it reads and holds the text and those ranges: on the 56 MB file `first(inputs)` takes 0.36 s and 205 MB (was 4.0 s and 952 MB), and on a 7 MB file 57 ms (was 428 ms), measured on an Apple M5 Max (interleaved min of 5, a loaded box, so read the ratios). A program that reads every document costs what it did. A stream with a BOM, `-s`, `--stream`, `--seq` or `-R` keeps the up-front route and its error placement, and one with a parse error keeps its clean start lazy and the up-front route for the rest (#5853, below); jq 1.7.1 agrees on 2,624 stream-by-program rows.
That route also no longer makes two more whole-stream passes before the filter runs: the end-of-stream marker (#4303) is read off the document ranges it already found instead of a strict re-scan, and each document's line is counted when it is read, with nothing kept per unread document. On an AMD Ryzen 9 7950X (interleaved min of 7, a loaded box) `first(inputs)` on a 77 MB NDJSON file takes 229 ms and 117 MB (was 578 ms and 194 MB) and on 9.7 MB 35 ms (was 79 ms), and `reduce inputs` is 5-7% faster with a third less peak memory.
On an Apple M4 Pro (interleaved min of 7) the same change takes `first(inputs)` on a 63 MB NDJSON file to 125 ms and 104 MB (was 286 ms and 204 MB) and on 7.9 MB to 19 ms (was 38 ms), and programs that read every document are 9-10% faster with peak memory halved.
The same route (#5854) now builds one index per run of consecutive documents (16 KiB of text for the first run, doubling to 1 MiB) and converts each document from its root in that index, instead of building and dropping an index for every document. `reduce inputs`, `last(inputs)` and the like over an NDJSON file of small records are 13.5-15.8% faster on an AMD Ryzen 9 7950X and 7.2-8.6% faster on an Apple M4 Pro (interleaved min of 11, 8 MB and 64 MB; 0 output differences; peak memory unchanged), and `first(inputs)` is unchanged within noise (+0.6% to +1.7% on the 7950X, -0.6% to +0.4% on the M4 Pro) because its first run is small.
A program that reads `input`/`inputs` without `-n` takes the same route (#5855), since its driver loop already pops its documents from the queue the program's own `input` draws from, and the strict end-of-stream scan is skipped for it as well. `jq -c '[., input_line_number] | halt'` on a 64 MB NDJSON file takes 0.12 s (was 0.82 s) on an Apple M4 Pro and 0.12 s (was 1.41 s) on an AMD Ryzen 9 7950X, and a program that reads every document is 4-8% faster on the M4 Pro (`[., input] | length` 1.37 s against 1.46 s) and 19-36% faster on the 7950X (`[., input] | length` 1.66 s against 2.60 s, `input_line_number` 2.31 s against 3.20 s); interleaved min of 7, output identical, and the same programs under `-n` do not move. A stream the route turns down (one that is malformed from its first quarter, or begins with a BOM), `-s` and `--stream` keep the up-front route. None of 4,840 rows (22 programs, 22 streams, 5 flag sets, a file and stdin) answers differently from the build before the change, and 1,622 rows that jq 1.7.1 answers the same are pinned.
A stream that turns malformed after a clean start keeps that start lazy too (#5853): the documents before the first fault are converted when the program reads them, the eager route reads the stream from the end of the last of them, and a number or literal directly before the fault is left to it, since jq never reads one the fault's own byte completes. `-nc 'first(inputs)|.id'` over a 64 MB NDJSON file with a stray `}` on its last line takes 236 ms and 133 MB on an AMD Ryzen 9 7950X (was 3.89 s and 1,078 MB) and 220 ms and 130 MB on an Apple M4 Pro (was 2.67 s and 896 MB); with the `}` in the middle 1.14 s and 606 MB (was 3.04 s and 1,027 MB) and 713 ms and 560 MB (was 1.92 s and 961 MB), and with it 30% in 1.53 s and 786 MB (was 2.78 s and 1,070 MB) and 901 ms and 733 MB (was 1.63 s and 918 MB) (interleaved min of 7 to 11, 0 output differences). The start is kept only when it covers a quarter of the stream: a fault within the first quarter of the file takes the eager route as before, because keeping the text alive for next to no lazy work held 2% to 9% more memory (a program that reads every document after a fault has the same peak, +0.6% to -4% across the faulted files; `[inputs]|length` at a 30% fault is 1,071 MB before and 1,025 MB after on the 7950X). Clean streams are unchanged.
A clean stream of several files takes the route too (#5857): one source per file, each with its own source tag and line count, so a token that runs on from one file into the next (#4316), an empty file and the end-of-stream marker read from the last file are all as before. A file the route turns down, a file that is not UTF-8 or `--validate` sends the whole stream to the up-front route. `-nc 'first(inputs)|.id'` over four NDJSON files (8, 32 and 64 MB in all) takes 25.3, 96.3 and 189.4 ms on an AMD Ryzen 9 7950X (was 194.2, 906.9 and 1,803.7 ms; peak memory 24, 56 and 99 MB, was 99, 366 and 720 MB) and 23.0, 86.0 and 172.4 ms on an Apple M4 Pro (was 114.4, 452.0 and 914.6 ms; 17, 51 and 105 MB, was 90, 347 and 695 MB). The driver loop without `-n` (`[., input_line_number] | halt`) moves the same (-87% to -89% on the 7950X, -80% to -81% on the M4 Pro), `reduce inputs` and `last(inputs)` are 11-13% faster on the M4 Pro and 44-47% faster on the 7950X with a fifth of the memory, and two and eight files read as four do. A single file does not move in time (-1.7% on the 7950X, +0.3% on the M4 Pro); its peak memory is +4.4% (2.3 MB of 53 MB) on the 7950X and unchanged on the M4 Pro. Interleaved min of 11, 0 output differences against the build before the change and against jq 1.7.1 on 16 rows per chip, the control run (the build before the change against itself) within -1.4% to +2.4% on the 7950X and -0.3% to +1.4% on the M4 Pro.
The scan that decides which documents of a single file are lazy no longer runs over the whole stream before the first input is read (#5856): it covers a chunk of text at a time (64 KiB for the first, doubling to 512 KiB), the two parsers are checked against each other over each chunk alone, and the producer scans the next chunk when it has read the last, forgetting the byte ranges of the documents it has read, so a program that stops early pays for the chunks it read. A fault met by a later chunk is read eagerly from the end of the last lazy document, as one the first chunk meets is, and the end of the stream is settled when the scan reaches it; the documents the eager reader finds after a fault are handed out as they are read, where they were copied into a second queue beside the vector they came from. `-nc 'first(inputs)|.id'` over a 63 MB NDJSON file takes 10.1 ms on an Apple M5 (was 128.5 ms) and 28.5 ms on an AMD Ryzen 9 7950X (was 119.0 ms), and over a 7.5 MB file 3.4 ms (was 16.4 ms) and 5.0 ms (was 14.4 ms). With a stray `}` at the 10% mark of the 63 MB file it takes 10.7 ms (was 1,298 ms) and 30.2 ms (was 2,499 ms), in the middle 9.1 ms (was 755 ms) and 29.0 ms (was 1,356 ms), and on its last line 10.1 ms (was 223 ms) and 28.1 ms (was 241 ms) (interleaved min of 7, 0 output differences in every configuration). A program that reads every document of such a stream is 13% faster on the M5 and 14% faster on the 7950X when the `}` is at 10%, since the first tenth is no longer read eagerly (`reduce inputs as $r (0; .+1)` 1,172 ms against 1,353 ms, and 2,202 ms against 2,565 ms). The peak memory of `first(inputs)` over the 63 MB file is 74 MB (was 119 MB; 1,113 MB with the `}` at 10%), of `reduce inputs as $r (0; .+1)` 76 MB (was 120 MB), and of the same program over a stream with a `}` at 10% 965 MB (was 1,113 MB), on an Apple M5. Programs that read every document of a clean stream cost what they did within 2% on the M5 and 1.5% more on the 7950X (`reduce` 1,320 ms against 1,300 ms, with the instruction count unchanged within 0.5%); over a stream with a fault, 2.1-3.0% more on the M5 and 0.7-5.2% more on the 7950X for a fault on the last line or in the middle.
