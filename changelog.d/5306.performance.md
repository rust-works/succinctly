- **jq: `group_by(f)` over an array keeps its groups as document nodes** (#5306). It went through the `eval.rs` bridge, which re-serialised and re-indexed the whole array, decoded every element into a `(key, element)` pair and then into groups: twice `sort_by`'s time and, with every element held decoded, more memory than jq (1,000 MB against jq's 668 MB on a 70 MB document). The keys are now read off the cursors, only the cursors are sorted and cut into groups, and a group stays on its cursors for what reads it: a printed result is written from the document, `length` counts the groups, `.[n]`, `first`, `last` and slices hand groups on undecoded, `map(f)` runs `f` over each group's cursors to the end (a failing, breaking or halting `f` stops where it does in jq, and a later `first` cannot skip it), and `.[]` yields the groups undecoded. A group is decoded only when a stage has to hold it as a value. yq mode, a non-array input and an alias-bearing document take the earlier route. Under `--preserve-input` the groups echo their source spelling, as `sort_by`'s elements do (a repeated key stays). Measured on an AMD Ryzen 9 7950X and an Apple M4 Pro (release builds, interleaved, min of 9, output identical to the earlier build; the unchanged `sort_by(.age) | length` row stays within +1.4% on both): see the pull request for the tables. `.users | group_by(.id % 100)` (every group printed) at 1 / 10 / 70 MB 23.7 / 243 / 2,633 ms → 11.5 / 108 / 1,147 ms on the 7950X and 18.1 / 158 / 1,783 ms → 10.9 / 82 / 839 ms on the M4 Pro; peak RSS at 70 MB of the `| map({k: .[0].id, n: length})` query 1,000 MB → 251 MB (7950X) and 970 MB → 251 MB (M4 Pro). A single group that holds every element is decoded whole by any stage that reads it, and `INDEX(.id)` is unchanged.
