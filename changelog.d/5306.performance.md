- **jq: `group_by(f)` over an array keeps its groups as document nodes** (#5306). It went through the `eval.rs` bridge, which re-serialised and re-indexed the whole array, decoded every element into a `(key, element)` pair and then into groups: twice `sort_by`'s time and, with every element held decoded, more memory than jq (1,000 MB against jq's 668 MB on a 70 MB document). The keys are now read off the cursors, only the cursors are sorted and cut into groups, and a group stays on its cursors for what reads it: a printed result is written from the document, `length` counts the groups, `.[n]`, `first`, `last` and slices hand groups on undecoded, `.[]` yields them undecoded, and `map(f)` runs `f` over each group's cursors when it only reads some of them (`.[0].id`, `length`) and over the group decoded once otherwise. `map` runs to the end whatever follows it, as in jq: a failing, breaking or halting `f` stops where it does there, and a later `first` cannot skip it. yq mode, a non-array input and an alias-bearing document take the earlier route. Under `--preserve-input` the groups echo their source spelling, as `sort_by`'s elements do (a repeated key stays). Measured on an AMD Ryzen 9 7950X and an Apple M4 Pro (release builds, interleaved, min of 9, output identical to the earlier build; the unchanged `sort_by(.age) | length` row stays within +1.6% on both). `.users | group_by(.id % 100)` printed in full, 1 / 10 / 70 MB: 23.7 / 245 / 2,625 ms → 11.5 / 108 / 1,144 ms (7950X) and 18.1 / 156 / 1,768 ms → 10.9 / 79 / 848 ms (M4 Pro); `| length` at 70 MB 2,278 → 989 ms and 1,375 → 732 ms; `| map({k: .[0].id, n: length})` at 70 MB 2,583 → 1,953 ms and 1,670 → 1,463 ms; `| map(.[0].id) | length` with one group per element 2,527 → 1,021 ms and 1,598 → 802 ms; `| map(.)`, which keeps every group, +3.0% on the 7950X and -14% on the M4 Pro. Peak RSS at 70 MB of the `map({k: .[0].id, n: length})` query 1,000 MB → 251 MB (7950X) and 970 MB → 251 MB (M4 Pro). A single group that holds every element is decoded whole by any stage that reads it (-4% to 0% time, 1,024 → 904 MB), and `INDEX(.id)` is unchanged.
