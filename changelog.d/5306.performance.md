- **jq: `group_by(f)` over an array keeps its groups as document nodes** (#5306). It went through the `eval.rs` bridge, which re-serialised and re-indexed the whole array, decoded every element into a `(key, element)` pair and then into groups: twice `sort_by`'s time and, with every element held decoded, more memory than jq (1,000 MB against jq's 668 MB on a 70 MB document). The keys are now read off the cursors, only the cursors are sorted and cut into groups, and a group is decoded when a later stage reads it (`map(f)`, `.[0]`, `length` decodes none) or printed straight from the document. yq mode, a non-array input and an alias-bearing document take the earlier route. Measured on an AMD Ryzen 9 7950X and an Apple M4 Pro (release builds, interleaved, min of 9, output identical to the earlier build; the unchanged `sort_by(.age) | length` row stays within +1.4% on both): `.users | group_by(.id % 100)` (every group printed) at 1 / 10 / 70 MB 23.7 / 243 / 2,633 ms → 11.5 / 108 / 1,147 ms on the 7950X and 18.1 / 158 / 1,783 ms → 10.9 / 82 / 839 ms on the M4 Pro; `| map({k: .[0].id, n: length})` 24.0 / 244 / 2,615 ms → 19.6 / 184 / 1,912 ms on the 7950X and 17.5 / 150 / 1,666 ms → 17.9 / 145 / 1,437 ms on the M4 Pro; peak RSS at 70 MB 1,000 MB → 251 MB (7950X) and 970 MB → 251 MB (M4 Pro) for the `map` and 1,000 MB → 262 MB and 910 MB → 343 MB for the printed array. A single group that holds every element (`group_by(.age)` over the generator's constant age) is decoded whole by any stage that reads it, so it is within -6% to +2% and 1,024 MB → 904 MB; `INDEX(.id)` is unchanged.
