- **jq: `--seq --stream` prints a record's parse-error warning before the open failure that follows its file, and not at all after the value that took the reader past a failure** (#6591). `jq -c --seq --stream . bad.seq missing` with `bad.seq` holding `\x1e1\n\x1e{"a\n\x1e2\n` printed `Could not open file missing` before `ignoring parse error: Truncated value at line 3, column 1`, and `jq -c --seq --stream . missing bad.seq` printed the warning although jq's main loop stops after the first event past the failure and never reads the fault. A plain run (no `-n`, no `-s`, a program that reads no `input`) now holds the failures it reports and prints each one before the first warning met in its own file or later, and drops a warning met reading any value after the one that took the reader past the first failure, as `--seq -s` did since #6603. Swept against jq 1.7.1 over 6 programs, with and without `-n`, and 819 file lists of up to three of nine `--seq` fixtures (complete, cut, faulted, missing), 9828 runs: `--seq --stream` differs in 154 where 292 did, and none the other way; `--stream`, `--stream-errors` and `--seq --stream-errors` are unchanged. What is left of that sweep is item 4: after a file whose last record is a top-level container with no newline (`\x1e[1]`), jq reads the closing event at the first missing file after it (`input_filename` names it) and stops there, so a later failure is not reported and a later file is not read; the pseudo-source that needs in the middle of a file list is the follow-up.
