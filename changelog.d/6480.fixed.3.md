- **jq: a last value that completes only at the end of the input is read at a last file that did not open** (#6480). jq's parser asks for more before a bare number or literal in the last bytes is complete, which sends its reader past the last file: `jq -c '[., input_filename, input_line_number]' nonl.json missing` over `1\n2` gives `[1,"nonl.json",1]` and then `[2,"missing",0]`, and `jq -c error num.json missing` over `12` prints the open error before `jq: error (at missing:0)`. succinctly named the last file that opened, at its line count, and said the open error after the last value's error. The last value is now placed at the missing file on the main loop, the `input` queue (eager and lazy, a file scanned a chunk at a time included) and `-R`'s lines when the last has no newline; under `-n` the read of that value reports the open error, so `jq -n input nonl.json missing` reads `1` and exits 0 rather than reporting the file up front. A string or container that ends on its own closing byte, and a value before white space, keep their file. `-R` without `input`, and a main loop whose program reads `input` or `input_line_number`, still report the file before the values. Pinned over 40 rows against jq 1.7.1 in `tests/jq_cli/i6480_last_value.rs`.
