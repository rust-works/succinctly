- **`succinctly jq` reports a NUL byte outside a string as a parse error at the NUL's own line and column** (#7966). This is ADR-0018's #7963 amendment E2, worded `Invalid character` as jq master words it (unreleased; commit fbee8f4, jqlang/jq#3606): `[1`, a NUL, `x,2]` is `jq: parse error: Invalid character at line 1, column 3`, exit 5, where jq 1.7.1 and 1.8.2 read `[1,2]` (their number parser reads the token as a C string) and jq 1.7.1 also dropped the rest of a newline-less read from the NUL on. The rule holds on every route that parses JSON input: the whole read, `input`/`inputs`, the windowed file and pipe routes, `--seq` (which no longer cuts a read at its first NUL, #7340), `--stream`, `fromjson`, `--slurpfile` and data imports. The token before the NUL is checked first, so `tr`, a NUL is `Invalid literal` and `-`, a NUL is `Invalid numeric literal`, at the NUL's column. A NUL inside a string, `-R`, `tonumber` and the `-f` program and module path rules are unchanged. The NUL-tail rewrite that emulated the releases (#7437, #7749, #7748, #7921, #7897) is removed, which closes #7904, #7922, #7937 and the first shape of #7948.
