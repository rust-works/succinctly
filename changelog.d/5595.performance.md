- **jq: `add` over an array no longer converts it twice and indexes it again** (#5595).
  `add` had no native arm, so the generic fallback converted the whole array, wrote it out as JSON, indexed that, and had `builtin_add` convert every element a second time from the new cursor;
  62% of `.numbers | add` over a 0.9 MB document was that detour.
  The array's elements are now converted once from the document's own cursor and folded with the same addition, in jq mode and while no variable is bound to a node of the document (an object, a scalar and `succinctly yq` keep the old route).
  `.numbers | add` over a 10 / 105 MB document of numbers went from 244 / 2429 ms to 87 / 846 ms on a 7950X and from 196 / 1863 ms to 79 / 727 ms on an Apple M4 Pro (jq 1.7.1 built from source: 181 / 1719 ms on the M4 Pro, where `succinctly jq` was 10% behind it before and is 2.3x ahead now);
  `.strings | add` over 9 MB went from 96 to 43 ms (7950X) and from 51 to 28 ms (M4 Pro).
  Release builds, interleaved, min of 11, output identical on all 16 configurations on each machine; `.numbers | max`, `.numbers | length` and `[.numbers[] | floor] | add` read within the control run's noise.
  An undecodable element is still reported ahead of an addition that fails earlier in the array, as before.
