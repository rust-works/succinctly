- **jq: a chain whose operands all call a `def` no longer re-walks itself once per operator** (#3997). `def f: .+1; map(f + f + ... + f)` re-asked `settles_before_consumer` of its whole left operand at every operator, up to the 1024-node analysis budget each time, so N terms cost N walks and doubled the time about 3-4x. The walk's answer is a function of the subtree alone, so each `Expr::Arithmetic` now remembers it with the nodes the walk cost (`ArithSettleMemo`), and a walk that reaches a remembered node charges the same cost and skips the descent. The result and the budget left are exactly what walking gives, so which operands settle (#3296, ADR-0025's `fib`/`sum_to` depth behaviour) is unchanged; only the settle analysis outside a `def` body remembers, a clone starts empty, and the memo is outside `PartialEq`/`Debug`. `map(<N terms>)` over 20,000 numbers, `succinctly jq` user time against the commit before, interleaved, min of 7-9: 25 / 50 / 100 / 200 terms 175 / 521 / 2,199 / 7,402 ms → 128 / 259 / 645 / 1,288 ms on an Apple M5 Max (-27% / -50% / -71% / -83%, about 2x per doubling) and 219 / 594 / 1,909 / 6,859 ms → 147 / 286 / 570 / 1,184 ms on a Ryzen 9 7950X (-33% / -52% / -70% / -83%); `succinctly yq` 100 terms -67% / -63%; a right-nested chain -71% / -69%; `sum_to(800)` and `fib(18)` within ±1.4% on both. Output identical to the commit before in jq and yq mode, and to `jq` 1.7.1.
