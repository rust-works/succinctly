- **yq: `key` and `parent` inside `with(PATH; . |= f)`, and inside any update nested in an update's filter, read the target's position** (#8039).
  `with(.b; . |= key)` is `.b |= (. |= key)`, and yq writes `"b"` there as it does for `.b |= key`, but the nested update answered no `key` at its own input, so `{"a":1,"b":5}` came back unchanged; `.b | . |= key` answered `5` for yq's `"b"`, and `with(.a.b; . |= (parent | keys))` left the node where yq writes the keys of `.a`. `key` is now the last component of the position the enclosing update installed, and `parent` climbs that update's input, so nested `with`, array members (`with(.a[]; . |= key)` is `[0,1,2]`), a missing target and `--eval-all`/`-i` agree. An update whose own reads cannot be resolved at its target now names that target for the updates nested in its filter, so `.x |= (.b |= (.c | . |= path))` is `["x","b","c"]` where it was `["x","c"]`. A value yq builds with no position (a scalar literal, an object constructor, `keys`) still gives a nested update none (`.a |= (.b |= (5 | . |= path))` is `[]`, as in yq). `with(.b; . |= (select(false) | key))` still leaves the input unchanged. `succinctly jq` is unchanged: `with` is not a jq builtin, and a nested update there still climbs no `parent`.
