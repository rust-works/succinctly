- **jq: `.[]` over an object no longer keeps a 144-byte field record per field, and `[.[]] | add` adds the object's values without decoding the whole array first** (#7290). `.[]`'s object arm built the duplicate-key-aware field list (key and value decoded, both cursors) and took the value cursors from it with an in-place collect, so the 32-byte cursors kept the whole list's buffer alive for as long as the result lived. It now walks the object keeping one value cursor and one key hash per field, reserves both at a bound read off the object's node subtree, hashes the keys 64 at a time, and collapses a repeated key (first position, last value, as jq 1.7.1 does) over those cursors in place, finding each key's slot by its own hash and confirming it against the key's text. `[.[]] | add` reached the decoding fallback, which built every element as an owned value with a copy of each number's spelling before the sum ran; it now takes the document array's streaming sum, which reads each number after the first as its value alone. `any`/`all` over an object take the same walk. Over one `wide` object (about 82,000 keys per MB), interleaved with an A/A control, output identical to jq 1.7.1's, `[.[]]|add` on an AMD Ryzen 9 7950X: 34.7 -> 15.4 ms and 27.3 -> 13.9 MiB at 1 MB, 308 -> 125 ms and 174 -> 53 MiB at 10 MB, 2746 -> 1174 ms and 1546 -> 405 MiB at 100 MB (jq 1.7.1: 5084 ms, 1331 MiB); on an Apple M4 Pro 22.8 -> 13.1 ms and 26.2 -> 6.5 MiB, 175 -> 87 ms and 202 -> 46 MiB, 1602 -> 821 ms and 1848 -> 398 MiB (jq 1.7.1: 3271 ms, 1449 MiB), with instructions halved. At 100 MB on the M4 Pro an object repeating a key every 1,000 keys falls from 2796 to 1113 MiB and 2260 to 1400 ms, one of eight keys repeated throughout from 1843 to 580 MiB at the same time, one whose values are all containers from 926 to 338 MiB and 586 to 557 ms, and `[.[] | [.[]] | add]` over 1.7 M six-key objects from 4135 to 1785 ms.
