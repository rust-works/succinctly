- **jq: `.[]` over an object no longer keeps a 144-byte field record per field, and `[.[]] | add` adds the array's elements without decoding it first** (#7290). `.[]`'s object arm built the duplicate-key-aware field list (key and value decoded, both cursors) and took the value cursors from it with an in-place collect, so the 32-byte cursors kept the whole list's buffer alive for as long as the result lived. It now walks the object keeping one value cursor per field and its key hash, on the stack for an object of up to eight fields and hashed 64 at a time past that, and collapses a repeated key (first position, last value, as jq 1.7.1 does) over those cursors in place, finding each key's slot by its own hash and confirming it against the key's text. `[.[]] | add`, and any array built of document nodes followed by `add` (`[.xs[] | select(f)] | add`), reached the decoding fallback, which built every element as an owned value with a copy of each number's spelling before the sum ran; it now takes the document array's streaming sum, which reads each number after the first as its value alone. `any`/`all` over an object take the same walk. Over one `wide` object (about 82,000 keys per MB), interleaved with an A/A control, output identical to jq 1.7.1's, `[.[]]|add` on an AMD Ryzen 9 7950X: 34.9 -> 15.8 ms and 27.2 -> 13.9 MiB at 1 MB, 306 -> 125 ms and 174 -> 53 MiB at 10 MB, 2698 -> 1158 ms and 1546 -> 405 MiB at 100 MB (jq 1.7.1: 4896 ms, 1331 MiB); on an Apple M4 Pro 22.6 -> 13.1 ms and 26.2 -> 8.6 MiB, 173 -> 89 ms and 202 -> 67 MiB, 1606 -> 819 ms and 1848 -> 433 MiB (jq 1.7.1: 3220 ms, 1452 MiB), with instructions halved. At 100 MB on the M4 Pro, `[.numbers[]]|add` falls from 2233 to 706 ms and 1085 to 330 MiB, an object repeating a key every 1,000 keys from 2262 to 1397 ms and 2796 to 963 MiB, and `[.[] | [.[]] | add]` over 1.7 M six-key objects from 4114 to 1768 ms; objects of 0 to 8 fields iterated by the million are at or below base on both chips.
