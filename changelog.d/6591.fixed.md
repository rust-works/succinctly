- **jq: `--stream-errors` stops past the first open failure where jq's main loop does, and reads its end-of-text fault at a missing last file** (#6591). `jq --stream-errors -c . missing bad.json missing2` with `bad.json` holding `[1,` printed the open error for `missing2` as well as for `missing`; jq 1.7.1 reports only `missing`, because the main loop stops after `[[0],1]`, the first event past the failure, which is complete inside `bad.json` (the fault after it is never reached). The test used to ask for a file that is clean throughout. It now asks the stream reader whether the first event is the same whatever bytes the next file begins with (`[1,` is, `[1` and a bare `1` are not), reading a doubling prefix of the file up to 1 MiB, when the files before it end between tokens; a file before it that ends inside a string, a number or a literal hands the token on, and the next file is judged as before. Separately, the `Unfinished JSON term at EOF` event of a text whose last file did not open is read at that file, line 0, so `input_filename` names it where it named `null`. Swept against jq 1.7.1 over 10 programs and 359 file lists of complete, half-read, empty, BOM-led and missing files, 3590 runs: 95 differ where 210 did, and none the other way; `--stream-errors -s`, `--stream` and `--seq --stream-errors` are unchanged. The `--seq` rows of the issue (items 3 and 4) are left to #6603 and #6609. A 3762-run matrix of first files cut inside every kind of token against next files that continue them agrees with `main` everywhere. Pinned over 19 rows in `tests/jq_cli/i6591.rs`.
