- **jq: reading a document array more than twice is O(1) per read** (#4035). `.users[0]`, `.[5]`, `$root.nodes[.from]`, `length`, `last`, `keys` and `has` resolved the index through a walk of the whole array, so a program that used a document array as a lookup table was quadratic: `. as $r | .users[] | $r.users[0].id` took 73 s on a 7 MB `users` document, and `[.[range(0;300)]] | length` over one 1M-element array 4.3 s on a 7950X. A wide array (64+ elements) that has been walked twice is now indexed on its third length lookup (the node id of every element, built by the same checked walk, so a malformed array still raises exactly what it raised), and later reads are O(1). 0.7 MB / 2.8 MB: 1,115 ms / 17.7 s -> 22 ms / 83 ms on a 7950X and 852 ms / 13.5 s -> 17 ms / 57 ms on an M4 Pro; the 300-read array row 4.28 s -> 71 ms and 3.23 s -> 52 ms. Read once or twice, an array costs what it did (instructions +0.00% to +0.29% for a single read, +1.5% / +1.7% for the worst case, an array read exactly twice). Numbers and the 7950X placement caveat in `docs/parsing/json.md`.
