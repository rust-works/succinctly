- **jq: a program that reads `input` reports an unopened file when jq's reader reaches it, not up front** (#6525). `jq -c 'try input catch .' missing.json three.json m2.json` printed the open error for `m2.json` as well as for `missing.json`; jq 1.7.1 reports only `missing.json`, because its main loop reads the first file before the program does and stops one value past the first failure, so the file after it is never opened. The same holds for `[., input_filename, input_line_number]`, `first(inputs)` and `[inputs]`, and for a failure between two files that opened, which is now reported when a read reaches it, after the values before it. A file that ends in a bare number or literal (`1\n2\n3`) still reports every failure after it up front. Swept over 120 file lists with failures before, between and after the opened files and 11 programs against jq 1.7.1 (2,520 runs): 158 differ before and 142 now, none the other way, and every one left holds a file that ends in a bare number or literal before a failure. Pinned over 20 rows in `tests/jq_cli/i6525.rs`.
