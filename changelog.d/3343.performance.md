- **jq: `length`, `keys | length` and the identity print of a wide object no longer scan each key twice or sort every key hash** (#3343). `census`, the key-only walk behind those queries, found each key's closing quote once to hash it and again to check the `:` after it; one scan now answers both (`keys_unsorted` shares it). It also sorted all `n` key hashes to learn that none repeats; from 128 to 2^21 keys a bitset prefilter now sorts only the few hashes that land on a bit another hash had set, with the sort as the fallback, so the answer is the same. On perf-guard's 2 MB `wide` fixture (159 K keys) `length` falls 12.2% in instructions on a 7950X (245.6 M to 215.7 M) and 9.3% in wall-clock (median, interleaved), the identity print 6.5% and 6.3%, `keys_unsorted` 2.5% and 2.9%; on an M4 Pro `length` -9.0%, `.` -6.8% (10 MB: -12.3% and -8.3%). `map(length) | add` over equal objects of 32,768 keys: -10.6% (7950X), -11.8% (M4 Pro); 8 keys per object is unchanged (the prefilter starts at 128). Output is identical, error text and exit status included, across 1,098 comparisons on 122 documents. Peak RSS rises by up to 0.6 MB at 159 K keys and 3.1 MB (5%) at 1.9 M. An exactly sized hash table (4% to 12% slower on the 7950X), an in-place radix partition (slower on both) and a gap-scan fast path (3% slower on the identity print) were measured and not kept; see `docs/parsing/json.md`.
