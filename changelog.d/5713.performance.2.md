- **jq: a named string argument is shared, not copied at each `$s` read** (#5713). `--arg`, `--rawfile` and a string `--argjson` were written into the expression as a literal, then copied again at each evaluation, so a program that read an 84 MB `--rawfile` twenty times held twenty copies. `succinctly jq` now promotes the string to shared storage once when it reads the arguments, and the literal, a `def` parameter and the `$ARGS` object hold a refcount to it. Against `main` at `f62dd98f6` plus the first #5713 entry, on a Ryzen 9 7950X (interleaved min of 5, output identical): an 84 MB `$s|length` runs 130 -> 60 ms and peaks at 91 MB instead of 250 MB; `[range(20)|$s|startswith("a")]` runs 750 -> 50 ms (1770 -> 95 MB); `def f($x): [$x,$x]|length; f($s)` runs 220 -> 50 ms (490 -> 92 MB); `-n --rawfile s <48 MB file> '$ARGS.named.s|length'` peaks at 74 MB instead of 312 MB; `$s|test("zzzz")` runs 380 -> 270 ms. Only a top-level string is shared: a string inside a `--slurpfile` or `--argjson` container, a JSON data module binding, builtins that take ownership of the string (`ltrimstr`, `ascii_downcase`, `sub`, `tojson`) and `succinctly yq` still copy. Appending to a short named string (`$t + "x"`) costs no more than before. ARM64 was not measured. **Library users:** `Literal::String` now holds a `SharableString` instead of a `String`; it dereferences to `str` and converts with `From`/`.into()` (`into_string()` gives the `String` back), and `Literal::string` takes `impl Into<SharableString>`. `succinctly yq`'s own `build_args_var` and the `-R`/`-Rs` input bridge are still built as before.
