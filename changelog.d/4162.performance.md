- **jq: a computed-index loop over a wide array in a path context is linear, not quadratic** (#4162). A non-negative index read in a path context (`[range(0;length) as $i | getpath([$i]) | tostring | key | 0]`, `[range(length-1;-1;-1) as $i | .[$i] | key | 0]`) makes no length lookup, so #4035's element index never served it and each read walked to its index: 14 s at 64,000 elements, 4x per doubling, ascending and descending alike. An array read that way is now answered from a prefix of element ids that the reads extend: a read inside it is O(1), a read beyond it resumes the walk where the last one stopped, so no element is walked twice. It starts on an array's third wide read, as #4035's index is built on the third length lookup, and the value route (which reads the length first) stays on #4035's rule. 16k / 32k / 64k elements: 936 ms / 3.65 s / 14.4 s -> 31 / 61 / 121 ms ascending and 909 ms / 3.60 s / 14.3 s -> 11 / 22 / 43 ms descending on a 7950X, 908 ms / 3.56 s / 14.1 s -> 31 / 56 / 106 ms and 887 ms / 3.51 s / 14.1 s -> 11 / 19 / 32 ms on an M4 Pro. An array read once or twice costs what it did, bar registering it (+1.2% / +1.4% instructions over 20,000 hundred-integer arrays, wall-clock -3.9% to +1.3%); one read exactly three times pays for recording and gains nothing from it (+4.7% / +6.1% instructions, +0.1% / +3.8% wall-clock on hundred-integer arrays, the worst case). Numbers and the 7950X placement caveat in `docs/parsing/json.md`.
