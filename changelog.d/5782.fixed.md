- **jq: dropping a value built millions of levels deep no longer aborts the process** (#5782). `succinctly jq -n 'reduce range(10000000) as $i ([]; .[0] = .) | length'` overflowed the native stack in `OwnedValue`'s drop glue (exit 134) and now prints `1`, as does the object form (`.a = .`). jq 1.7.1 segfaults on the same program from a few hundred thousand levels (between 150,000 and 200,000 on macOS with an 8 MB stack), so there is nothing to match (ADR-0018). A per-thread count of nested container drops lets a shallow value drop through the ordinary glue as before; once 256 are running, the rest of the value goes onto a heap worklist, so a drop needs at most about 54 KB of native stack. As first written (#5815), the count cost about 1% of instructions on queries that build and drop millions of small containers (`[.users[] | [[[.id]]]]`) and -0.4% to +2.2% wall-clock on a 7950X over 10 and 100 MB inputs. Releasing the container's storage inside the count instead (#5868) cut the registers `OwnedValue`'s drop glue saves from ten to six (four before #5782); on the 7950X that removes about half of the count's extra instructions on the container-heavy queries (`Ir` against the code before #5782: `[.users[] | [[[.id]]]]` +0.90% to +0.50%, `[.users[] | {a: ., b: [.]}]` +1.05% to +0.45%), and wall-clock is within the control's spread (median row +0.85% against the code before #5782, +0.6% against #5815, where an identical binary measured -0.5%). On an M4 Pro the median row is then -0.3% against the code before #5782: rows that build and drop several containers per record are +0.3% to +3.2% (`[.users[] | [[[.id]]]]`, three arrays per record, +3.2%, where each unique container pays one macOS thread-local address lookup) and the rest are -0.9% to -2.5%.
