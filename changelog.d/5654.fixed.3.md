- **jq: `arr | map(f)` and `obj | map(f)` refuse a bad gap they pull past** (#5654, #1641 residual). `[1@,2] | map(.)`, `[1,,2]`, `[1,2,]`, `[1 2]`, `{"a":1,"b":2,}` and `{"a":1,"b"}` answered at exit 0 because the lazy source read the elements through a cons list that ran no gap check; jq 1.7.1 refuses each as a parse error, and `succinctly jq` does now, with jq's messages. An object is checked whole, by the probe that already finds a repeated key (a repeated key included), at no extra walk. An array is checked as it is pulled, so a consumer that stops early (`first(.[])`, `map(.) | first`) never sees a bad gap after its answer, and a gap inside a child `f` never reads is not seen; matching jq there would validate the rest of the array for a filter that exists to stop early. Cost, retired instructions on an Apple M5 Max (min of 5, release, not wall-clock; x86_64 not measured): `map(.) | length` over 3M integers +6.5%, `map(.+1)` +4.2%, `map(.[0])` over short arrays +3.0%, an object of 1M members +2.1%, and `.users | map(.id)` / `map(select(...))` over 14 MB of records +2.5% / +1.2%; unrelated paths move by layout alone (`[.[]] | length` +2.3%, `.[]|select(...)` +1.5%), and `length`, `.[100]`, `first(.[])` are within 0.1%.
