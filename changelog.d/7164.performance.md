- **jq: `--seq` over a pipe on standard input is read a window at a time, so its peak memory no longer grows with the stream** (#7164, the last route of #7024). `cat records.seq | jq --seq -c .` over a pipe or socket holding 4 MiB or more read the whole stream: 121 MiB at 100 MiB of RFC 7464 records on an M4 Pro (a laptop route check, not a benchmark), where a regular file has been flat since #7082. Each record is now certified when the RS after it (or the stream's end) is read, with the check the whole-file route makes, and the windows of certified records are read with each RS as a space: 11.8 MiB at 100 MiB. A pipe cannot be read twice and output cannot be taken back, so at the first record that is not `RS value LF` (or one over 64 MiB) the windows stop before it and the rest of the pipe is read whole by the route that walks jq's reader, resumed where jq's reader stood after the records already run (the line, the `fgets` chunks and the stale byte of jq's token buffer that a bare `n` reads), so every warning, value, `(at <stdin>:N)` line and the end-of-stream drop come out as for the stream read whole. A stream that turns only near its end now runs its clean prefix on the lazy route: 152 to 11.9 MiB, and faster. Checked against the same pipe read whole by unit tests of the resumed reader over 4,000 generated streams, the gate over every read size and probe cut, CLI tests pinned to jq 1.7.1, and `scripts/jq-windowed-file-fuzz.py --pipe --seq`. A pipe under 4 MiB, `-s`, `--validate` and `-n` still read the stream whole.
