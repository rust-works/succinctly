- **jq: `$ENV` and `env` read the environment once per thread, where they built the whole object again on every evaluation** (#6560). Every name and value was copied, inserted into a new map and allocated for each record, so `$ENV.HOME` over 100 MB of NDJSON (about 850,000 records) cost more the bigger the shell's environment, and `select(.name == $ENV.HOME)` was several times slower than jq. The CLI now calls `snapshot_environment()` at startup, so the object is built on a thread's first use and each later `$ENV` is a clone of it; a library caller keeps reading the current environment unless it opts in. Against jq 1.7.1, interleaved, on a Ryzen 9 7950X (100 MB, 14 variables): `$ENV.HOME` 2046 to 701 ms (jq 1178 ms, so 0.58x became 1.7x); with 94 variables 8193 to 709 ms (jq 1167 ms, 0.14x became 1.6x); `select(.name == $ENV.HOME) | .id` with 94 variables 9841 to 1172 ms (jq 1243 ms). On an Apple M4 Pro (93 variables) `$ENV.HOME` 7273 to 485 ms (jq 1374 ms, 0.19x became 2.8x). jq's own `env.HOME` rebuilds the object per call, so it is now 16x to 24x ahead of jq with 93 variables.
