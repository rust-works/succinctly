- **jq: under `--seq`, a program that stops early reads only the records it consumes** (#7775).
  `--seq -n 'first(inputs)'` read and walked the whole stream before its first record ran, so it cost as much as
  `[inputs]` and grew with the input, where jq reads a line at a time and stops at the records the program takes.
  A program that calls `input`/`inputs` now walks the stream as it reads it, a block at a time, from named files
  or a pipe, so `first(inputs)`, `limit(n; inputs)`, `input | halt` and `first(inputs | select(...))` stop after
  the blocks their records are in, and answer while a pipe is still open, as jq does. Each named file is opened
  only when the walk reaches it, as jq's reader opens it, so a run that stops early never opens the files after
  its records (a named pipe with no writer among them). Each record is let go once the program has it, so
  `-n 'reduce inputs as $x (0; .+1)'` over a pipe holds a few reads however long the stream (its peak is the same
  at 1 GB as at 100 MB), where it held the whole stream and grew with it. A main loop that can halt (`.id, halt`) no longer reads a file whole to vouch for it before its
  first record: it is read a window at a time from the start; over a pipe it is walked as it is read too, so it
  answers at the record it halts on where it waited for 4 MiB or the pipe's end, and one that never halts stays
  as small. None reads past the records it consumes, so a fault later in the stream is not met, as jq never
  meets it, and every answer is unchanged. Instruction counts (cachegrind, the AMD Ryzen 9 7950X box): `--seq -n
  'first(inputs)'` is 6.6 million at 10 MB and at 100 MB, where it was 817 million and 8.08 billion; `--seq -c
  '.id, halt'` over a 10 MB file is 12.1 million, where it was 326 million.
