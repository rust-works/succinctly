- **yq: a write through N aliases of N different anchors is linear, not quadratic** (#6869). `.m[].p += 1` over `l: [&a0 {p: 0}, &a1 {p: 1}, ...]` / `m: [*a0, *a1, ...]` grew about fourfold per doubling of N: the alias table's redirect bound, asked for every path component of every fanned-out path, summed the alias count of every group on each call (a single anchor with N aliases, as in #6839, made that sum one term). The bound is now computed once where the table is built. Release builds, interleaved A/B, output identical on every row (`ab-cli.py`, 5 repetitions, medians; another session's single-core `rustc` was running on each box, aggregate CPU 89-97% idle, and a base-against-itself control read within ±1%): on a 7950X `.m[].p += 1` at 2,000/4,000/8,000 anchors reads 27/72/221 ms before and 17/34/71 ms after, `.m[] |= (.p += 1)` reads 20/50/141 ms before and 15/30/63 ms after; on an M4 Pro 19/66/241 ms before and 15/26/49 ms after for the first, 15/43/138 ms before and 12/22/42 ms after for the second. After, the time doubles with N out to 64,000 anchors (621 ms on the 7950X, 367 ms on the M4 Pro). A 30,000-element plain document is unchanged on both (`.items[] |= (.b = 7)`: -0.5% and +0.2%).
