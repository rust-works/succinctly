- **jq: a `reduce`/`foreach` that destructures its loop variable with literal object keys converts only the members the pattern names** (#5544, item 1 of #5519's follow-ups). `reduce .users[] as {score: $s} (0; . + $s)` converted each element whole (every member hashed into a map and allocated) before the pattern picked one; an object pattern whose keys are all literal (`{score: $s}`, `{$score}`, `{id: $i, name: $n}`) now takes the same projection as `$u.field` (#5519): the element becomes an object holding only the named members (at most 8; more converts it whole). Interleaved A/B on `users` documents of 1.4, 7 and 51 MB, identical output, against the tip of `main`: `reduce .users[] as {score: $s} (0; . + $s)` -30% to -32% on a 7950X and -31% to -34% on an M4 Pro, a two-key pattern -20% / -21%, the `{$score}` shorthand -31%, a `foreach` -27% to -34%; the M5 Max reads -19% to -34% across the same rows. A pattern naming a computed key, an array pattern, a `?//` alternative, one naming more than 8 keys, a whole-element loop variable (`$u`) and a non-fold query are within about 1% of a same-binary control. jq mode over JSON only. **A member the pattern does not name is no longer decoded**, so an undecodable one (`[{"a":"\ud800","b":5}]`) that jq refuses at parse time no longer fails `reduce .[] as {b: $b} (0; . + $b)`, as with #5519. A malformed element still fails the fold. Recorded in `docs/compliance/jq/limitations.md`.
