- **yq: a parenthesised `..` write over many aliases of different anchors is linear, not quadratic** (#6883). `(.. | select(tag == "!!int")) |= . + 1` over `l: [&a0 {p: 0}, &a1 {p: 1}, ...]` / `m: [*a0, *a1, ...]` grew about threefold per doubling of N: the descent's paths that lie below an alias position (yq's `..` does not go into an alias) were removed from the resolved list with a scan and a shift per path, each step a deep expression comparison. They are removed in one pass now, matched by a byte key counted in a multiset (one entry per mention, as the scan did; an ordered map, since the crate is `no_std`). Release builds, interleaved A/B, output identical on every row (`ab-cli.py`, 5 repetitions, medians; a base-against-itself control read within ±1.2%; the 7950X was idle, a Chrome renderer held one core of the M4 Pro): on a 7950X the rows at 2,000/4,000/8,000 anchors read 52/156/528 ms before and 28/56/111 ms after; on an M4 Pro 45/135/460 ms before and 22/40/75 ms after. After, the time doubles with N out to 64,000 anchors (979 ms on the 7950X, 598 ms on the M4 Pro). A 30,000-element plain document is unchanged on the M4 Pro (-0.1% median over three update and read rows) and reads +1.0% on the 7950X, where `.items | length`, which never reaches this code, reads +2.4%: the binary's layout, not this change. The boxes timed a build that used a hash map for the multiset; the shipped ordered map was only timed in a debug build, 0.52 s against 0.51 s at 8,000 anchors.
