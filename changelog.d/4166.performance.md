- **jq: `[.[] | ., 1]`, `[.[] | ., . | length]` and `[.[] | (., .)?]` keep the nodes they hold instead of decoding them** (#4166). #3922's `,`-stage array route took only a pipe of pure navigation, so a computed branch beside a navigation one, a computed stage after navigation branches, and a `?` around a group of navigation branches ran the owned route and decoded every node the array holds. The route now takes each shape whose order it keeps: computed branches with nothing after them, navigation branches with any tail, and `(a, b)?` over navigation, where a catchable raise ends that output's group as in jq. On a 14 MB `users` document, release, Apple M4 Pro mini, interleaved A/B with identical output (min wall): `[.users[] | ., 1] | length` 173.5 ms -> 37.6 ms (`-78%`) and 182 MB -> 46 MB, `[.users[] | ., length] | length` 211.4 ms -> 70.5 ms (`-67%`), `[.users[] | ., . | length] | length` 285.1 ms -> 109.4 ms (`-62%`), `[.users[] | (., .)?] | length` 306.8 ms -> 36.9 ms (`-88%`) and 290 MB -> 42 MB; the holdouts (`[.users[] | ., .]`, `[.users[], 1]`, `[.users[] | .id, .name]`, an owned prefix that declines) read within `+-1.4%` (median, idle re-run, 21 reps). Over an unreadable value `[.[] | ., 1] | length` and `[.[] | (., .)?] | length` now answer like `[.[] | ., .] | length`; printing the array still raises. jq mode only.
