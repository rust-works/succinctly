- **jq: a plain filter over a pipe on standard input reads it a window at a time, so its peak memory no longer grows with the stream** (#7024, #6920). `cat log.ndjson | jq -c .` (a pipe or socket holding 4 MiB or more; no `-n`, no `input`, no `--slurp`, `--validate` or `--seq`) read the whole stream and split every document into a span first, about 124 MiB at 100 MiB of NDJSON on x86_64, because a regular file words its first fault by reading itself again and a pipe cannot. Each window is now certified before it is dropped: a document the strict validator accepts is one jq's parser reads without a fault, and only a document it turns down is read by jq's parser model over the bytes as read. So the first fault is worded as the whole stream words it, even where it sits in a document the filter never read and the window that held it is gone (checked against the same pipe read whole by unit tests over random streams at six window sizes, CLI tests and `scripts/jq-windowed-file-fuzz.py --pipe`). A pipe under 4 MiB, a terminal, `-R` over a pipe and `--seq` over a pipe still read the input whole, and a run that stops early now leaves the rest of the pipe unread, as jq does. The windows are certified on a thread of their own (#7106), over a copy of each, so the filter does not wait for the validator: measured interleaved at 100 MiB with an A/A control (which moved 1.1% at most), peak RSS falls from 125 to 21-23 MiB on a Ryzen 9 7950X and from 123 to 18 MiB on an M4 Pro, while `-c .` is 4.8% and 5.1% faster than the route that read the pipe whole, `-r .name` 2.3% and 4.9%, and `select(.score>50)` 3.7% and 3.2% (certifying on the filter's thread cost 2% to 17% instead). A regular file, several files and a pipe under 4 MiB start no thread.
