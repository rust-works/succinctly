- **jq: the experimental call machine (`SUCCINCTLY_CALL_MACHINE=1`) is bounded by the memory the process holds, and no longer bounds a loop's outputs** (#8064, part of #7977).
  `succinctly jq` samples its own resident memory as the machine runs (`/proc/self/statm` on Linux, the physical footprint on macOS) against a limit computed once per process from what the machine has: the least of half the physical memory, half the cgroup's `memory.max`, and a quarter of the room a `ulimit -v` cap leaves.
  Past it a run is refused with `f/0: memory limit exceeded`, so the ten memory repros of #8064, which grew past 3 GB when the budget charged a slot per collected value, are refused near any limit they meet (at a limit of 1.5 GiB, at 1,027-1,545 MiB peak RSS on an Apple M5 Max), and a capped run refuses instead of aborting on an allocation the machine does not make.
  The input document counts toward the limit, and what one leaf builds within one evaluation is seen only when it ends.
  The shipped tail loop's `MAX_LOOP_OUTPUTS` bound is no longer the machine's: a loop past 2^20 outputs answers as jq 1.7.1 does (`[def f: if . < 1048577 then ., (. + 1 | f) else . end; 0 | f] | length` is `1048578`), where `SUCCINCTLY_CALL_MACHINE=0` still refuses it with `f/0: maximum outputs exceeded`; a library caller that installs no memory probe keeps the output bound.
  `MAX_LOOP_ROUNDS` is unchanged, and nothing changes with the switch off.
