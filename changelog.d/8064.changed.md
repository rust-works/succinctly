- **jq: the experimental call machine (`SUCCINCTLY_CALL_MACHINE=1`) bounds what a run holds by bytes, and no longer bounds a loop's outputs** (#8064, part of #7977).
  The machine counts the heap a run holds as the allocator counts it: its control state and every value it keeps, `[...]` accumulators, a leaf's buffered outputs, a `reduce`'s and a `foreach`'s state and bindings, with nested containers, strings and objects at what they hold, and a value shared with one already held counted once (`$big` collected thousands of times answers).
  The `succinctly` binary installs a metered system allocator for it, which outside a machine run reads one atomic per allocation and counts nothing.
  Past 1.25 GiB, or half the room a `ulimit -v` cap leaves, a run is refused with the recursion wording, so the ten memory repros of #8064, which grew past 3 GB when the budget charged a slot per collected value, are refused at 0.5-1.5 GB peak RSS on an Apple M5 Max, and a capped run refuses instead of aborting on an allocation the machine does not make.
  The shipped tail loop's `MAX_LOOP_OUTPUTS` bound is no longer the machine's: a loop past 2^20 outputs answers as jq 1.7.1 does (`[def f: if . < 1048577 then ., (. + 1 | f) else . end; 0 | f] | length` is `1048578`), where `SUCCINCTLY_CALL_MACHINE=0` still refuses it with `f/0: maximum outputs exceeded`.
  `MAX_LOOP_ROUNDS` is unchanged.
