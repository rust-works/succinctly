- **jq: a keyed lookup into a wide document object is a hash probe, not a walk of its members** (#3913). `.big[$k]`, `$b[.]` for a `$b` bound to a node of the document being read, `getpath(["big", $k])` and a literal `.big.k` each walked every member of `big` on every lookup, so 10,000 lookups into a 10,000-key object took 3.5 s (350x the same read once `tostring` made the key an owned value and `$b` the decoded map). The first lookup of an object that proves wide (64 or more members) still walks; the second builds a per-object key index in one pass over the keys alone (no member value is decoded, so validation stays where something reads it), and every later lookup is one probe. An object the walk would raise on (a non-string key, an unpaired tail, a stray trailing comma) is never indexed, so the same lookup raises the same error it always did, a repeated key still resolves to its last occurrence, and only the winning member's own `,`/`:` delimiters are checked, as before. Measured on an Apple M4 Pro, release build, 10,000 lookups, min of 3: `$b[.]` 0.61 s -> 0.11 s at 1,000 keys and 3.46 s -> 0.09 s at 10,000; `.big[$k]` 0.62 s -> 0.10 s and 3.60 s -> 0.09 s, within noise of the `tostring` row at both sizes; the index costs about 32 bytes per key (3 MB at 100,000 keys). At most four indexes and two million members are kept per evaluation; a wider object keeps the walk. Single-lookup shapes are unchanged to within the ±1% layout band (`.big.k5000.v` -0.1% instructions, `.users[0].name` 0.0%, `keys_unsorted` -0.1%, `to_entries` 0.0%; `.users[].name` and a `select` over every record read +0.5% to +1.3% instructions with wall-clock inside noise). JSON documents only: YAML mappings keep the walk, and `has($k)`/`path(.big[$k])` have their own walks.
