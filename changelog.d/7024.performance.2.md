- **jq: a plain filter over several regular files reads them a window at a time, so its peak memory no longer grows with the files** (#7024, #6920). `jq -c . a.json b.json` (up to 32 regular files, 4 MiB or more between them; no `-n`, no `input`, no `--slurp`, `--validate` or `--seq`) read every file whole and split every document into a span first: 225 MiB for one 100 MiB file named twice on x86_64 and 255 on aarch64, where jq holds 3. It now holds one 1 MiB window and the document being run, 10.2 MiB on x86_64 and 6.7 on aarch64, flat from 10 MiB to 100 MiB, and reads 8% to 12% faster on x86_64 and 2% to 5% on aarch64 (a control run read within 1%). The files are read as the one stream jq reads them as: a token open where a file ends continues at the front of the next, and the file `input_filename` and a diagnostic name, the line a runtime error names and the wording of the first fault are the whole-file route's, checked on over 2,000 random streams cut into 1 to 32 files with BOMs, invalid UTF-8 and faults. A pipe on standard input, more than 32 files, a list with a path that is not a regular file and `-R` or `input`/`inputs` over several files still read the input whole. A regular file that is also standard output or error (`jq . f 1<>f`), alone or among several, is read whole now, as a standard input of that kind already was, since its output would land where the next window is read from; a file whose `stat` size is 0 and which has content (`/proc`) is read to its end.
