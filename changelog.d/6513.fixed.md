- **jq: `--seq` and `--stream` word the error for a bare `n` after a string with a multi-byte escape as jq does** (#6513). `printf '\x1e"\u00e9"\n\x1en\n' | jq --seq -c .` says `Invalid numeric literal` in jq 1.7.1 and `Invalid literal` here, and so does `printf '"\u00e9" n\n' | jq -c --stream .` (also with `-s` and with `--stream-errors`). jq decodes a string's escapes in place over its token buffer, so what its parser reads at index 1 when it classifies the next bare `n` is the second byte of the decoded text: a `u` (the escape for `A` decodes to one byte and leaves its `u` there) takes the keyword path (`Invalid literal`), and anything else the number path (`Invalid numeric literal`). Both parsers kept the raw bytes of the string, which agrees with jq only when the string has no escape or its escape decodes to one byte, so a string holding an escape for `U+00E9`, a lone surrogate, a surrogate pair, or `A` followed by another character gave the wrong wording. They now share one decode that writes the decoded text over the token buffer as jq does, including the part decoded before an invalid escape. Only the wording differed; stdout and the exit status were the same. A differential of random strings against `/usr/bin/jq` found 14 to 22 differences per 1,500 cases in each of `--seq`, `--stream`, `-s --stream` and `--stream-errors` before, and none after.
