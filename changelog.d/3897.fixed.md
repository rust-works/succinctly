- **jq: a fold's loop variable is usable in path position when its source navigates below INIT's node, on the stdin route** (#3897).
  `echo '[{"a":1}]' | jq 'reduce .[] as $x (.; del(.[0] | $x))'` is `[]` in jq, because `$x` is the very `jv` the source yielded and
  `.[0]` of the accumulator is the same one; the stdin route refused it (`Invalid path expression`), as it did `reduce .a as $x (.; del(.a | $x))`, because INIT and
  the source were materialized from the cursor separately and the embed table (#2889) only reused a node's own `Rc`, never a descendant of one it holds. A fold's INIT entry now also
  answers a materialization of any container below its node with the matching child of INIT's value, so the source yields the `Rc` the accumulator holds (`-n 'input | ...'` already did).
  Only a fold that marks its loop variables registers a descending entry, and only its first INIT fork. A member a later one shadows (`{"a":1,"a":2}`) and an empty container or scalar below INIT
  keep refusing where jq answers; a computed INIT with no cursor (`{k:.} | .k`) is unchanged. jq mode only; yq is unchanged.
