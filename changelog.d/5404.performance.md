- **jq / yq: a parenthesized pipe over computed values is linear in its stage count, not quadratic** (#5404).
  A pipe of `n` stages that runs over values the program computed (`[range(0;20000) | (. + 1 | . + 1 | ...)]`)
  rebuilt an owned `Expr::Pipe` of the rest of the pipe for every value at every stage, and each copy re-ran the
  analyses a pipe asks of itself. A pipe that a second value goes down now keeps the copy of each tail it hands on
  (pipes of up to 128 stages and tails of up to 1,024 nodes; a tail holding a `def` is still copied per call), and
  remembers the three syntactic facts the owned re-entry walked the whole rest for. This covers the route that
  collects a pipe's outputs (an array constructor, `add`-style consumers); a pipe driven one output at a time
  (`select`, `limit`, `first`, `reduce` over it) and a tail ending in a user `def` call are unchanged. 20,000
  values on an Apple M5 Max, interleaved min of 3 CPU seconds, output identical: n=20 0.658 s -> 0.158 s, n=40
  1.714 s -> 0.268 s, n=80 5.444 s -> 0.451 s (the flat spelling at n=80 is 0.46 s); 200,000 values through a
  10-stage pipe 1.146 s -> 0.401 s (-65.0%), through a 3-stage pipe -19.1%, through 2 stages unchanged. A body
  rebuilt for each value (`. as $x | (...)`) is within +2.3%, and document-sourced pipes within noise. On an AMD
  Ryzen 9 7950X: n=20 0.641 s -> 0.153 s, n=40 2.206 s -> 0.306 s, n=80 8.338 s -> 0.606 s; the 10-stage pipe
  1.418 s -> 0.597 s (-57.9%), the 3-stage pipe -17.8%.
