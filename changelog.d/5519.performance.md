- **jq: a `reduce`/`foreach` whose update reads its loop variable only as `$u.field` converts just those members of each element** (#5519). Each element was converted whole (every member hashed into a map and allocated) for a body that read one of them; the element is now an object holding only the fields the update and extract read (at most 8; more converts it whole), found in one checked pass over its members. Interleaved A/B on `users` documents of 1.4, 7 and 51 MB, identical output, against the tip of `main`: `reduce .users[] as $u (0; .+$u.score)` -28% to -36% on an M4 Pro and a 7950X (51 MB: 570 ms to 363 ms and 650 ms to 439 ms), a loop variable nothing reads (`.+1`) -61% to -74%, `reduce ... .[$u.name] = $u.score` -18% to -23%, a `foreach` update -29% to -36%, `. + ($u.score | floor)` -22% to -31%. On 20-member records, reading 1, 5 and 8 fields is -44%, -33% and -26% on the 7950X and -49%, -30% and -21% on the M4 Pro. A fold that reads `$u` whole (`[$u]`, `$u | length`), one naming more than 8 fields, a scalar source and a non-fold query are within about 2% of a same-binary control, apart from one row on the M4 Pro that runs no new code. jq mode over JSON only. **A member the fold does not read is no longer decoded**, so an undecodable one (`[{"a":"\ud800","b":5}]`) that jq refuses at parse time no longer fails `reduce .[] as $u (0; .+$u.b)`; `.[] as $x | $x.b` and `.[] | .b` already answered the same. The object's own frame (keys, delimiters, tail) is still checked, so a malformed element fails the fold as before. Recorded in `docs/compliance/jq/limitations.md`.
