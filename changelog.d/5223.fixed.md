- **jq: `path`, `del`, `pick` and the assignment operators answer as jq 1.7.1 does when their target is more than plain navigation** (#5223). A jq program whose path target binds, folds, branches, retries a `?//`, catches an error or calls a function (`del(.users[] | .score as $s | select($s < 100))`, `path(. as $x | foreach ... | $x)`, `(.a | if .b then .c else .d end) |= 9`) now runs on a path-mode interpreter that carries jq's path register `(path, value)` with every output and checks it with jq's pointer identity where jq does, instead of the resolver inferring the register and refusing (`Invalid path expression ...`, exit 5) wherever it could not prove jq's answer. Rows the resolver refused or answered differently now match jq, which closes #4800, #5013, #5030, #5042, #5044, #5101, #5113, #5175, #5181, #5194, #5203, #5207 and #5213; navigation targets (`.a.b`, `.[]`, `.[2:4]`, `..`) and value filters over them (`select(.score < 100)`, `//`, `first`, `try ... catch empty`) keep the streaming walkers, so `del(.users[] | select(.score < 100))` costs what it did. Recorded divergences, in `docs/compliance/jq/limitations.md`: a walk jq never finishes raises the existing caps (`null | [path(recurse(.a))]` now raises `recurse: maximum nodes exceeded` where it used to answer `1`), and a write to an unshared array slice builds a new array where jq writes the slice in place. See ADR-0026.
