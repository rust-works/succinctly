- **jq: `select`, `if` and `tojson` after a computed number no longer write the number out and index it again** (#5602, #5601 follow-up).
  `[.numbers[]|.+1|select(.>10)]` wrote each `.+1` result out as JSON and indexed it to run the `select`. For a computed `Int` or `Float`
  (not a NaN, not a document's literal) the condition is now settled from the number, as `owned_select_door` does on the sink route, `if`
  takes its branch from the same verdict, `else empty` yields nothing, and `tojson` is the number's `tostring`. A condition outside the
  pure grammar (a generator, a path) bridges as before. Over a generated `numbers` document (Apple M5 Max, interleaved min, 1 and 10 MB,
  jq 1.7.1): `.+1|select(.>10)` 0.61x -> 1.39x of jq, `.+1|if .>10 then 1 else 0 end` 0.58x -> 1.27x,
  `.*2|select(.>10 and .<500000)|.+1` 0.64x -> 1.55x, `floor|select(.>10)` 0.91x -> 2.56x and `.+1|tojson` 0.72x -> 1.18x.
  An array constructor or an `as` binding after a computed number still bridges.
