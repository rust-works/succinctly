- **jq: a clean `--seq` stream is proved clean by a record check instead of the whole-stream walk** (#6501, #6437 follow-up).
  `--seq` input takes the NDJSON route when jq's reader would read it without a diagnostic (#5674), and to decide that it ran a byte-at-a-time model of jq's reader over the whole stream (about 200 MB/s) before the route scanned every document again. A stream that is RFC 7464's own framing, every record `RS value LF` with the value one RFC 8259 document, now skips the walk: the strict validator (about 1 GB/s) reads each record, last record first, and three guards (the stream starts on an RS, ends on a newline, and every record ends on a newline) close the ways valid records can still leave the stream unclean. Any other stream takes the walk exactly as before. A fuzz holds the check to the walk under both `-s` values (3,000,000 streams, 6,000,000 checks, 0 unsound) and drops each guard in turn to show it is needed.
  On an AMD Ryzen 9 7950X (jq mode, min of 21 interleaved runs, `json generate -p json-seq --seed 6437`, output identical on every row), 1 / 10 / 100 MB: `--seq -r .name` 12.8 / 115.7 / 1150 ms to 9.7 / 84.6 / 817 ms (-24% / -27% / -29%); `--seq -s -c length` 10 / 100 MB 81.3 / 816 ms to 50.0 / 490 ms (-39% / -40%). A stream the check cannot vouch for pays about nothing when it fails at its last record (a truncated tail: 450 / 4348 ms to 449 / 4321 ms; a last record that is not RFC 8259, such as `nan`: 116 / 1151 ms to 116 / 1142 ms). A stream that fails earlier costs the records before the failure, read at the validator's speed, and plain NDJSON, which this does not touch, read -1.6% / -2.0%.
