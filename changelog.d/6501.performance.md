- **jq: a clean `--seq` stream is proved clean by a record check instead of the whole-stream walk** (#6501, #6437 follow-up).
  `--seq` input takes the NDJSON route when jq's reader would read it without a diagnostic (#5674), and to decide that it ran a byte-at-a-time model of jq's reader over the whole stream (about 200 MB/s) before the route scanned every document again. A stream that is RFC 7464's own framing, every record `RS value LF` with the value one RFC 8259 document, now skips the walk: the strict validator (about 1 GB/s) reads each record, and three guards (the stream starts on an RS, ends on a newline, and every record ends on a newline) close the ways valid records can still leave the stream unclean. Any other stream takes the walk exactly as before. A fuzz holds the check to the walk under both `-s` values (3,000,000 streams, 6,000,000 checks, 0 unsound) and drops each guard in turn to show it is needed.
  On an AMD Ryzen 9 7950X (jq mode, min of 21 interleaved runs, `json generate -p json-seq --seed 6437`, output identical on every row), 1 / 10 / 100 MB: `--seq -r .name` 12.8 / 115.9 / 1148 ms to 9.7 / 84.8 / 826 ms (-24% / -27% / -28%); `--seq -c .` 11.3 / 102.5 / 1011 ms to 8.3 / 71.4 / 691 ms (-27% / -30% / -32%). The cost lands on a stream the check cannot vouch for: one whose last record draws a warning (10 / 100 MB: 449 / 4315 ms to 465 / 4471 ms, +3.6%), and one the walk reads as clean but whose last record is not RFC 8259 (`nan`; 116 / 1152 ms to 129 / 1276 ms, +10.9%). A record that fails early costs nothing measurable. Plain NDJSON, which this does not touch, read -1.6% / -2.0%.
