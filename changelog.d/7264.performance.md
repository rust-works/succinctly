- **jq: `first(inputs)` over a file no longer scans 64 KiB before it hands out the first record** (#7264, refs #7260). The lazy input scan started on a 64 KiB first chunk and a 256 KiB read of the file, each document checked by two parsers against each other (about 3,600 instructions per 85-byte record): 2.9 M of the 3.9 M instructions of `-n 'first(inputs)|.id'`, where `-n 1` is 1.1 M. The first chunk is now 4 KiB and doubles to the unchanged 512 KiB cap, and a file longer than the 256 KiB front is first read on 16 KiB (reading on to the front when the first chunk does not fit, and the rest of the front as the first window, read onto the text's own buffer so no page is touched twice). `-n 'first(inputs)|.id'` over an NDJSON file takes 1.035 ms against 1.242 ms on a Ryzen 9 7950X at 10 MB (-17%; jq 1.7.1 1.071 ms; about 1.35 M instructions against 3.94 M, callgrind) and 1.923 ms against 2.025 ms on an Apple M4 Pro (-5%; jq 1.643 ms), flat from 1 MB to 100 MB, and `-n 'input|.id'` 1.004 ms against 1.232 ms (7950X) and 1.962 ms against 2.073 ms (M4 Pro). Which files try the lazy start (those longer than 256 KiB) does not change, but a stream whose first fault or invalid UTF-8 lies past the first 4 KiB chunk now takes the lazy route and meets it in a later chunk or window, where it used to be read whole by the eager route; the output is the same (29,640 differential runs against the previous binary, byte for byte). On the 7950X `reduce inputs` and `[inputs]|length` read 1-3% slower than the base's default layout and 0.1% faster to 0.3% slower than the base laid out differently (`-align-all-functions=6`); an independent placement test of 12 layouts per source judged it code placement (about 80-85% sure), and the M4 Pro rows do not move.
