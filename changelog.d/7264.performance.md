- **jq: `first(inputs)` over a file no longer scans 64 KiB before it hands out the first record** (#7264, refs #7260). The lazy input scan started on a 64 KiB first chunk and a 256 KiB read of the file, each document checked by two parsers against each other (about 3,600 instructions per 85-byte record): 2.9 M of the 3.9 M instructions of `-n 'first(inputs)|.id'`, where `-n 1` is 1.1 M. The first chunk is now 4 KiB and doubles to the unchanged 512 KiB cap, and a file longer than the 256 KiB front is first read on 16 KiB (reading on to the front when the first chunk does not fit, and the rest of the front as the first window, read onto the text's own buffer so no page is touched twice). `-n 'first(inputs)|.id'` over an NDJSON file takes 1.045 ms against 1.267 ms on a Ryzen 9 7950X at 10 MB (-17%; jq 1.7.1 1.087 ms; 1.35 M instructions against 3.94 M, callgrind) and 1.849 ms against 1.962 ms on an Apple M4 Pro (-6%; jq 1.587 ms), flat from 1 MB to 100 MB, and `-n 'input|.id'` 1.026 ms against 1.242 ms (7950X) and 1.868 ms against 1.966 ms (M4 Pro). Interleaved A/B of 1,200 `posix_spawn` runs with an A/A control, output identical to the old binary and to jq 1.7.1. `reduce inputs`, `[inputs]|length` and `-n 1`, eleven `--arg`/`--argjson` and `yq -n 1` startup do not move on the M4 Pro; on the 7950X the two whole-stream rows read 2-3% slower in this build, which is not the short start (a build with the start switched off reproduces it at 5-8%) and is under test as a code-placement effect.
