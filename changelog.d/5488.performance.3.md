- **jq: a body rebuilt for each value that reads its variable late no longer re-walks the rest of its pipe at every stage** (#5488, third step).
  The pipe-level questions the owned re-entry asks of each tail (does it hold a `TrackedVar`, does it hold a node that can start a resolver invocation) were answered by walking the tail's stages, because a `true` is not inherited from the pipe a tail was copied from.
  For a body that reads its variable in its last stage that is a walk over the whole rest, once for each of the `n` calls.
  A pipe whose stages are shared storage now finds the stages that hold either once for the whole storage, and each tail reads its answer from there, so the walk is paid once per value.
  On an Apple M4 Pro (release, min of 7 interleaved wall-clock runs, `[range(0;20000) | . as $x | (<n stages>)] | add`) at n = 10 / 20 / 40 / 80: `[.][0]` stages with the read last -6% / -13% / -25% / -38% (1.129 s to 0.696 s at 80, now linear), `floor` stages with the read last -10% / -22% / -39% / -56% (1.070 s to 0.470 s).
  On an AMD Ryzen 9 7950X (same method): `[.][0]` stages with the read last -4% / -11% / -25% / -39% (1.672 s to 1.021 s at 80), `floor` stages with the read last -7% / -19% / -32% / -48% (1.310 s to 0.682 s), both linear.
  The read-first controls are within ±2% on both machines, and the every-stage row reads +1% to +5% on both, the cost of finding the marked stages once per value when every stage holds the variable.
