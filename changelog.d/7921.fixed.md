- **A caught input fault or a NUL in a number where jq's 4,095-byte read ends no longer gives values jq never gives** (#7921). Three rules of jq's reader were modelled in one place and not in another. (1) A byte-order mark is skipped by jq's parser but is in its first `fgets` read, which so holds 4,092 bytes of text; the search for the token a file leaves open for the next file ran before that share was recorded, so with a mark, 4,090 spaces and `l 1` in one file and `BB BF 3` in the next, `[limit(6; repeat(try input catch .))]` gave the fault, then `1`, then a second fault, where jq 1.7.1 and 1.8.2 give the two faults: the `1` is open at the end of the file and the next file's bytes go on with it. (2) A number with a NUL in a read that holds no line break (a line longer than the read) was left a malformed token: `}`, a newline, 4,091 spaces, `1`, a NUL, `x`, a quote and then `8` and `9` on their own lines gave the fault, `Unfinished string at EOF`, `8` and `9`, where both jq releases give the fault, `1` and the unfinished string. The number is now read wherever the two releases agree on it: the read hides only the rest of the token and white space and the next read starts with a byte that ends a token, or the token goes on into the next read with another NUL. (3) Behind a mark cut across files (`EF BB`, then `BF 1`, a NUL, `x`) the pass that reads such a number saw the mark's last byte as the token's first, and the run ended in `Invalid JSON text` where jq prints `1`. All three predate this release; a program that does not read past input errors was affected only by (2) and (3), as an error where jq has a value. Still different, and recorded in `docs/compliance/jq/limitations.md`: the alignments of (2) in which jq 1.7.1 and 1.8.2 differ from each other, a read boundary after an invalid UTF-8 byte on a long line (an extra error), and a NUL-ended number at the end of a file with no newline (#7922).
