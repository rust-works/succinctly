# ADR-0016: Reject SIMD Escape Scanning for jq Format Functions

## Status

✅ Accepted

## Context

**Issue**: [#663](https://github.com/rust-works/succinctly/issues/663) (this measurement), a
precursor to [#124](https://github.com/rust-works/succinctly/issues/124) (SIMD escape scanning
for jq's format functions).

#124 already landed a real, measured win: rewriting `@uri`/`@html` from per-`char` `push` loops
to byte-oriented bulk-span copies (`5824025d`, `9ee4b58d`) fixed a genuine 12-15x bottleneck,
architecture-neutral across M4 Pro and 7950X. That work is unaffected by this ADR.

#124's *remaining* scope proposes going further: instantiating this crate's shared SIMD escape
scanner (`find_json_escape` / `define_escape_scanner!`, `src/util/simd/escape.rs`) for
`@uri`/`@html`/`@csv`/`@dsv`/`@sh`, to find the next escape-triggering byte in a 16/32-byte chunk
instead of scanning byte-by-byte. The projected "4-12x on no-escape strings" / "2-4x end-to-end"
numbers are carried over from O3's *YAML→JSON transcoding* workload, not measured on
format-function inputs.

Per #124's own 2026-07-30 reconciliation comment, this is exactly the shape of trap the
ADR-0007/ADR-0013 representativeness gate exists to catch — the same gate previously rejected
#122 on measurement: "real JSON strings are p50 = 7 bytes, p90 = 17, with only ~7% reaching the
32-byte AVX2 chunk width." Format-function inputs *might* be shaped differently — `@csv`/`@dsv`
rows in particular could plausibly be long — but "plausibly" is exactly what the gate exists to
replace with a number. This is at least the sixth time a micro-benchmark or borrowed figure has
been checked against real input shape in this codebase (P2.6, P2.8, P3, P5, P8, #647); every
prior case where a benchmark number wasn't re-measured against the target workload cost real
engineering time to unwind.

## Decision

We will **not** implement SIMD escape scanning for `@uri`, `@html`, `@csv`, `@dsv`, or `@sh`.
Like ADR-0007 and ADR-0013, this decision is made at the **analysis stage, before writing any
kernel**, on measured evidence.

### Measured input shape

Reproducible via:

```bash
./scripts/sync-bench-corpus.sh
cargo run --release --example jq_format_shape
```

(`examples/jq_format_shape.rs` — measurement only, not linked into the library or CLI.)

**Primary pools** — the direct analogue of jq operating on values extracted from real parsed
documents:

- Every JSON string and YAML scalar in the pinned real-workload corpus (#301,
  `data/bench/corpus`, 7 JSON + 8 YAML files, n = 7004) for `@uri`/`@html`/`@sh`.
- Every DSV/CSV row field in the same corpus (2 files, n = 10899) for `@csv`/`@dsv`.

**Supplementary pools** — narrower but on-point real corpora for `@uri`/`@sh` specifically: 259
URLs referenced from this repo's own `docs/**/*.md` (including this ADR's own links, since the
tool walks the tree as committed), and 858 quoted literals from non-comment lines of this repo's
own `scripts/*.sh`.

Escape predicates mirror `src/jq/eval.rs` exactly: `format_uri`'s ASCII-alnum + `-_.~` safe set,
`format_html`'s five-entity set, `quote_csv_field`'s unconditional quote-wrap (shared by
`format_csv`/`format_dsv`, so the delimiter choice does not change this analysis) plus
embedded-`"` scan, and `format_sh`'s unconditional quote-wrap plus embedded-`'` scan.

`len >= 32B` is the ADR-0007/ADR-0013 chunk-width threshold. **Longest safe run** is the more
precise SIMD-relevant quantity — the longest span of non-escape-triggering bytes a bulk-copy scan
could actually exploit, which can be much shorter than the string itself.

| format                                  | n     | p50 len | p90 len | p99 len | max len | len ≥ 32B | 0-escape strings | longest safe run ≥ 32B |
| --------------------------------------- | ----- | ------- | ------- | ------- | ------- | --------- | ---------------- | ---------------------- |
| `@uri` (generic string values)          | 7004  | 8       | 18      | 64      | 330     | 3.5%      | 86.3%            | 0.8%                   |
| `@html` (generic string values)         | 7004  | 8       | 18      | 64      | 330     | 3.5%      | 99.5%            | 3.2%                   |
| `@sh` (generic string values)           | 7004  | 8       | 18      | 64      | 330     | 3.5%      | 99.7%            | 3.4%                   |
| `@csv`/`@dsv` (DSV row fields)          | 10899 | 6       | 11      | 16      | 33      | 0.0%      | 100.0%           | 0.0%                   |
| `@uri` (real URLs, `docs/`)             | 259   | 51      | 63      | 89      | 106     | 89.2%     | 0.0%             | 3.1%                   |
| `@sh` (real shell literals, `scripts/`) | 858   | 15      | 61      | 97      | 130     | 26.2%     | 94.8%            | 25.1%                  |

### Interpretation

None of the 5 formats' realistic inputs clear the ~32-byte AVX2 chunk-width threshold for a
meaningful share of their corpus, on either the direct length measure or the more precise
run-length measure:

- **`@uri`/`@html`/`@sh` (primary pool, n = 7004).** Only 3.5% of strings even reach 32 bytes
  overall, and the SIMD-relevant metric — longest contiguous run of non-special bytes — clears 32
  bytes in just 0.8-3.4% of strings. 86-99.7% of strings need *zero* escaping under each format's
  rule, i.e. there is nothing to scan around in the overwhelming majority of cases.
- **`@csv`/`@dsv` (primary pool, n = 10899 real DSV fields).** 0.0% of fields reach 32 bytes, and
  not a single field in the corpus contains an embedded quote — consistent with
  [corpus-shape.md](../benchmarks/corpus-shape.md)'s existing "quoted fields: 0.72%" / "embedded
  quotes: 0" finding for the same corpus. The escape cost here is a **fixed** 2-byte quote-wrap
  paid unconditionally by every string field, not a function of scan length, so there is
  structurally nothing for a byte-skipping scanner to save even at larger field sizes.
- **Supplementary corpora.** Drawn from a different, narrower population (whole URLs and this
  repo's own script prose, not JSON/YAML-derived field values), these are individually longer
  (p50 51B and 15B) but the run-length metric stays low: 3.1% for URLs — a URL's own `:`/`/`
  structural characters break up otherwise-long domain/path segments under `@uri`'s strict
  unreserved-only safe set — and 25.1% for shell literals, the most favorable number measured.
  Even that is a minority share, and real `@sh` usage overwhelmingly formats extracted field
  values (the primary pool) rather than hand-written script prose, so the primary pool's 3.4% is
  the more representative figure for this format.

This extends the ADR-0007/ADR-0013 finding to jq's format functions: input length is necessary
but not sufficient for a chunk scanner to pay off; what matters is the run length between
escape-triggering bytes, and — like JSON strings and YAML flow collections before them — these
inputs are short enough, and (for `@csv`/`@dsv`) their escape trigger rare enough, that this
codebase's ~32-byte AVX2 break-even is essentially never reached.

## Consequences

- **#124's remaining scope is dropped.** SIMD escape scanning via `find_json_escape` /
  `define_escape_scanner!` instantiation is not implemented for any of the 5 format functions.
  #124's already-landed byte-oriented bulk-copy rewrite for `@uri`/`@html` is unaffected — this
  ADR concerns only the further SIMD step, not that prior, separately-measured win.
- `src/jq/eval.rs` is unchanged by this issue — measurement only, per #663's scope.
- `examples/jq_format_shape.rs` is retained as a reproducible, mirrored-predicate analysis tool,
  the same role `corpus_stats.rs` plays for the JSON/YAML/DSV shape gates in ADR-0013. Unlike
  `corpus_stats`, it is not CI-gated (no golden `--check`): it exists to answer this one question
  rather than to guard an ongoing invariant, so it is not wired into the corpus-shape CI check.
- Neutral: this ADR records a *non*-implementation. If a workload with genuinely long,
  escape-dense format-function inputs becomes common (e.g. `@csv` rows built from long,
  quote-heavy free text), it can be revisited with fresh corpus data.
