# ADR-0029: An Owned Array Is a Window on Shared Storage (#6659)

## Status

🟡 Proposed (2026-11-12). Extends [ADR-0024](adr-0024.md)'s structural sharing from whole arrays
to ranges of one. Measured on both architectures; see [Measurements](#measurements).

## Context

`OwnedValue::Array` held `ArrayOf<OwnedValue>`, a `Rc<Vec<OwnedValue>>` (#2999). Cloning the
handle shared the whole array, but a slice `.[a:b]` of an owned array built a new `Vec` holding
the range. jq's `jvp_array_slice` copies nothing: a `jv` carries a 16-bit `offset` and a `size`
beside its storage pointer, and a slice moves them. A loop that peels one element per step was
therefore linear in jq and quadratic here, and a loop that keeps each step's value held
quadratic memory. #6659 measured, on `[range(N)]` (7950X, jq 1.7.1):

| program                                    | N       | jq     | succinctly                     |
|--------------------------------------------|---------|--------|--------------------------------|
| `until(length<10; .[1:])`                  | 100,000 | 73 ms  | 1,258 ms                       |
| `def f: if length>10 then .[1:]\|f else length end; f` | 100,000 | 69 ms  | 233,219 ms         |
| `[while(length>10; .[1:])] \| length`      | 100,000 | 75 ms  | aborts (allocation failure)    |

Arrays read from the document were already lazy (#4195, #6231, #6258, #6265), and #5274 cut a
fold's uniquely owned state in place with a `memmove`. Neither changed what a slice of a
*shared* owned array is, and a `def`, `while`, `recurse` or `limit` always holds a second
handle on its input.

Facts that shaped the decision, measured against `main` at `6db201026`:

- **Where a `Vec` is needed.** Making `ArrayOf` deref to `[V]` instead of `Vec<V>` left 46
  compile errors in the library: the sites that grow, shrink or reorder the array (`push`,
  `truncate`, `drain`, `splice`, `retain`, `remove`, `clear`, `shrink_to_fit`, `capacity`, and
  16 calls passing an array as `&mut Vec`). The other ~1,050 `OwnedValue::Array` sites only
  read, and compile unchanged.
- **Where identity is read.** Array identity reaches the evaluator through two functions,
  `OwnedValue::shares_storage_with` (the embed table #2889, the resolver #3177) and
  `jq_identical` (`==`'s short circuit, #3069), both through `ArrayOf::ptr_eq`.
- **jq's rules**, from `src/jv.c` at `jq-1.7.1` and probed with `/usr/bin/jq`:
  - `jvp_array_slice` returns a fresh `jv_array()` for an empty range;
  - it copies the range into a new array once `offset + start` reaches 65,536 (the offset is
    an `unsigned short`), and otherwise adds `start` to the offset and sets the size;
  - `jv_identical` compares kind, offset, size and pointer, so two slices of one range are one
    node, `.[0:]` is the array itself, and `.[1:]` is not.
  - `path_mode.rs` already simulated these rules with two memo tables keyed by storage
    address (#5103), and `FoldNode::slice` models them for paths.

## Decision

**`ArrayOf<V>` is a window: `{ inner: ManuallyDrop<Rc<Vec<V>>>, start: usize, len: usize }`.**

- `Deref` yields the window's elements as a `[V]`. Its length comes from the handle, and its
  data pointer from the `Vec`. The bounds check is skipped, so the invariant
  `start + len <= inner.len()` is kept by construction:
  - every change to the `Vec`'s length zeroes the window first and sets it after, so a
    destructor that panics part-way through a `truncate` or `drain` leaves an empty window;
  - `slice` and `cut` check their range with a hard `assert!`, in every build.
- `DerefMut` yields a `&mut [V]`. A shared handle first copies its window, and nothing outside
  it, into storage of its own. A unique handle writes in place.
- `make_vec()` lends the `Vec` itself, through a guard, to the sites that change the length.
  It copies a shared window, or compacts a unique one in place. The guard zeroes the window
  while it is out and writes the `Vec`'s new length back when it drops, so a guard leaked with
  `mem::forget` leaves an empty window, not a dangling one.
- `slice(range)` is `jvp_array_slice`:
  - an empty range is a fresh `[]`;
  - the whole window is a clone of the handle (the same node);
  - a range starting 65,536 or more elements into the storage is copied into a new array;
  - any other range is a new window on the same `Rc` (a refcount bump).
  `path_mode.rs`'s `array_slice` is now this function, and its memo tables are gone.
- `ptr_eq` compares pointer, start and length, which is `jv_identical`.
- `cut(range)`, the fold step's in-place cut (#5274), moves a unique handle's window as
  `jvp_array_slice` moves an offset, and drops the cut-off tail at once. When the offset would
  reach 65,536, where jq copies, the head is compacted away and the offset starts from 0 again,
  as the copy's does. A loop peeling one element per step therefore moves each element at most
  once per 65,536 rounds, keeps fewer than 65,536 cut-off elements alive, and has jq's offsets.
- `push` and `Extend` append to a unique window in place and keep its offset, as
  `jvp_array_write` appends to an unshared view, so a queue (`.[1:] | . + [$x]`) never compacts.
  `make_vec`, for the other writes that change the length, compacts to offset 0, as jq's
  rebuilding writes (`del`, `splice`-shaped updates) start a new array.
- `OwnedValue::as_array` returns `&[OwnedValue]`, and `as_array_mut` returns the `make_vec`
  guard, which derefs to `Vec<OwnedValue>`. That is a public API change for the next 0.x minor
  (`changelog.d/6659.changed.md`).

The read-path slice builders (`slice_owned_value`, `getpath` with a slice descriptor, the
resolver's `node_below`, `get_value_at_path`, `truncate_stream`'s `jq_slice_from`) take
`slice`. Write paths that edit a sub-array and splice it back (`.[a:b] |= f`, `del(.[a:b][0])`)
still copy it: the sub-array must be unique for the splice to write in place.

One more change was needed for the `def` form, and it is not part of the representation.
`each_def_tail_loop` ran an `if` condition over a computed value through the re-index bridge,
which serializes the whole value to read one count. After the slice was O(1), that bridge was
the remaining O(n) per round. The tail walk now settles the condition with
`owned_cond_verdict` first, the pure-grammar verdict `until` and `while` already use (#3697),
in jq mode.

## Alternatives Considered

- **A separate `OwnedValue::ArraySlice` arm.** The handle would change less, but every one of
  the ~1,100 `Array` match sites that has a `_` arm would silently treat a slice as a non-array,
  and the compiler cannot find them. Under the window, a site that needs a `Vec` fails to
  compile, so none can be missed. Rejected.
- **`u32` start and length (a 16-byte handle).** jq's own size field is an `int`, but a 4G-element
  cap would need a refusal path, and the width saves nothing: `OwnedValue::String`'s payload is
  already 24 bytes beside `NumberRepr`'s niche, so `OwnedValue` is 32 bytes either way (pinned
  by `owned_value_is_32_bytes_because_its_containers_are_one_pointer_3000`).
- **A length sentinel instead of the guard** (`len == usize::MAX` meaning "the whole `Vec`").
  It costs a branch on every read to save the guard on the 46 writes. Rejected.
- **Only a front offset** (the window always runs to the end of the `Vec`). It covers `.[1:]`
  but not `.[:-1]` or `.[a:b]` of a shared array, and not jq's identity of an inner range.
- **`drain` in place, the issue's first layer.** Already in for a uniquely owned fold state
  (#5274). It cannot help `def`, `while`, `recurse` or `limit`, which hold a second handle, nor
  a program that keeps every tail.

## Consequences

- A slice of an owned array is O(1) time and memory in both modes; the elements were already
  shared by refcount.
- **Identity follows jq more closely.** An owned slice used to be a fresh node, so
  `[1,nan,2] as $a | $a[1:] == $a[1:]` was `false` where jq says `true`, and a path through a
  bound slice could not be recognized. Both now answer as jq does. Two residuals:
  - a value that crosses the re-index bridge loses its identity there, as it did before
    (`[$a[1:], $a[1:]] | .[0] == .[1]` is still `false`; jq says `true`);
  - a length-changing write through `make_vec` on a unique array (`remove`, `retain`,
    `truncate` at the evaluator's write sites) compacts to offset 0. Where jq's equivalent write
    keeps the offset instead, a later `.[n:]` crosses jq's 65,536 copy threshold at a different
    point. That is observable only through identity, on an array of 65,536 or more elements.
- **Retention.** A small window keeps its whole storage alive while another handle shares it,
  as a jq view does, and a unique one keeps fewer than 65,536 cut-off head elements alive, as a
  jq offset does. Before, a slice released the rest at once.
- **Every read takes its length from the handle** instead of the heap and offsets its data
  pointer by `start`. [Measurements](#measurements) has the cost on rows that read arrays
  without slicing them.
- `share_stats` still records every forced copy. A copy now copies only the window, so a copy
  of a shared slice costs its range, not its storage.

## Measurements

Measured 2026-11-12 on an AMD Ryzen 9 7950X (terminus) and an Apple M4 Pro (the M4 mini). Base
is `9cce7d9fe`, head this change (`8e55cc9db`); a second build of the base is the A/A control,
and all three are release builds from `git archive` on each box. `scripts/ab-cli.py` ran
interleaved, with output identity gated before any timing (0 differences in every run), under
an 8 GB memory cap. Both boxes were idle and on mains power.

**The issue's loops, on `.users | map(.id)` of a 1.4 MB `users` document (about 14,000 ids),
median of 3:**

| program                                         | 7950X base | 7950X head | M4 Pro base | M4 Pro head |
|-------------------------------------------------|------------|------------|-------------|-------------|
| `until(length < 10; .[1:])`                     | 30.6 ms    | 10.3 ms    | 48.7 ms     | 10.3 ms     |
| `reduce range(length - 10) as $i (.; .[1:])`    | 31.5 ms    | 11.1 ms    | 49.7 ms     | 10.3 ms     |
| `def f: if length > 10 then .[1:] \| f else length end; f` | 5,323 ms | 12.9 ms | 3,998 ms | 12.1 ms |
| `[while(length > 10; .[1:])] \| length`         | 4,515 ms   | 11.2 ms    | 1,724 ms    | 10.8 ms     |
| `[.[1:][]] \| length`                           | 12.6 ms    | 12.9 ms    | 11.4 ms     | 11.4 ms     |

**The scaling curve, `[range(N)] | <program>` with `-n`, min of 3 (head) or one run (base),
wall time including the memory-cap wrapper.** On head every program is at the floor of a bare
`length` over the same input (68 ms on the 7950X, 88-90 ms on the M4 Pro) at 25,000, 50,000
and 100,000 elements alike, so the work no longer shows against process start. Base, at
25,000 and 50,000:

| program (base)                      | 7950X 25k | 7950X 50k | M4 Pro 25k | M4 Pro 50k |
|-------------------------------------|-----------|-----------|------------|------------|
| `until(length<10; .[1:])`           | 121 ms    | 326 ms    | 210 ms     | 623 ms     |
| `def f: ... .[1:] \| f ...`         | 15,658 ms | 62,872 ms | 13,308 ms  | 54,342 ms  |
| `[while(length>10; .[1:])]`         | killed at the 8 GB cap | killed | killed | killed |
| `.[1:] \| . + [$i]` per round (queue) | 173 ms  | 685 ms    | 336 ms     | 1,220 ms   |

`[while(length>10; .[1:])]` at 25,000 elements peaks at 9.78 GB on base without a cap (5.9 s)
and at 13 MB on head; at 100,000 elements head peaks at 22.7 MB (7950X, `/usr/bin/time`). jq
1.7.1 peaks at 3.6 MB and 7.7 MB.

**Array reads that never slice**, where the window's offset is paid on every read: 8 queries
over the `users` document and 6 over the `arrays` one (`map(add)`, `flatten`, `map(reverse)`,
`group_by`, `to_entries`, indexed reads, ...), at 1.4 and 14 MB (`users`) and 1.3 and 13 MB
(`arrays`), 11 repetitions:

| run                    | 7950X control | 7950X head | M4 Pro control | M4 Pro head |
|------------------------|---------------|------------|----------------|-------------|
| `users`, median of medians | +0.11% (-3.7% .. +2.2%) | -1.02% (-2.8% .. +1.0%) | +0.16% (-0.5% .. +1.4%) | -0.07% (-1.9% .. +2.1%) |
| `arrays`, median of medians | +0.03% (-1.1% .. +1.0%) | -0.53% (-1.5% .. +2.1%) | -0.02% (-1.3% .. +1.3%) | -0.10% (-1.0% .. +0.6%) |

Both read-only runs are inside their control's band on both machines. One row sits just
outside it on the 7950X only: `[.[] | .[1:]] | length` over `arrays` reads +2.1% at 1.3 MB
(min and median) and +2.1% min / +0.9% median at 13 MB, against a control of -1.1% .. +1.0%,
and `[.[1:][]] | length` reads +2.1% / +3.0% in the 3-repetition loop run. Both build a slice
of every element and read it back. The same rows are neutral on the M4 Pro (-0.1%, +0.2%). It
is within the code-placement shifts x86 rows show at equal work (#3100), and it is not
removed here.
