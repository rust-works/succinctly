# ADR-0013: Reject the SIMD Chunk-Scanner JSON Validator (#130)

## Status

✅ Accepted

## Context

The JSON validator ([`src/json/validate.rs`](../../src/json/validate.rs)) is a purely scalar
recursive-descent parser. Issue **#130** proposed replacing it with the simdjson-style two-phase
design: a SIMD scanner producing 64-byte-chunk bitmasks (escaped bytes, true quotes, in-string
regions, structural characters), feeding an explicit state machine with an explicit nesting stack.

Its prototype — which lived only on the unmerged branch of PR #127 — measured **1.16–1.32×** on
UTF-8-heavy strings and **0.86–0.91×** (a regression) on ASCII-heavy structured objects.

Three of the issue's stated premises had gone stale by the time it was picked up:

- The AVX2 Keiser–Lemire UTF-8 validator it planned to salvage from PR #127 had already landed,
  better and differentially tested, in [`src/text/utf8.rs`](../../src/text/utf8.rs).
- The quote/backslash/control scanners it planned to salvage already existed as
  [`find_json_escape`](../../src/util/simd/escape.rs), across NEON/AVX2/SSE2/scalar.
- The `NestingStack` was justified as fixing the #151 recursion DoS, but #151 was already fixed by
  `MAX_NESTING_DEPTH = 128`.

Per [docs/guides/benchmarking.md](../guides/benchmarking.md), #130 is one of the perf issues gated
on the corpus-shape check. Following the ADR-0007 precedent, we ran that check before writing any
scanner code.

## Decision

We will **not** implement the SIMD chunk-scanner validator. Like ADR-0007, this decision was made
at the **analysis stage, before writing any kernel**, on measured evidence.

The deciding metric is not run length but **interesting density** — the number of positions the
state machine must visit per 64-byte chunk (structural characters outside strings, one visit per
string, one per atom start, plus garbage). A chunk scanner does not need long runs of skippable
bytes; it needs few visits per chunk.

Measured over the pinned real-workload corpus (5 JSON files, 971 KB) against current M4 Pro
throughput:

| corpus file           | visits / 64 B | current throughput |
| --------------------- | ------------- | ------------------ |
| pretty/3d-ribbon.json |           4.0 | **1.79 GiB/s**     |
| tabular/carshare-data |           8.0 | 1.21 GiB/s         |
| geojson/us-election   |          10.9 | 1.19 GiB/s         |
| charts/bullet-data    |          20.0 | 856 MiB/s          |
| graph/miserables.json |          24.0 | 789 MiB/s          |

Interpolating #130's own two measured points (1.16–1.32× at density ≈ 1; 0.86–0.91× at density
≈ 18–22) puts break-even at roughly **8–12 visits per chunk**. Every real corpus file falls on the
wrong side of that line, in one of two ways:

- **Below break-even, but no headroom.** `3d-ribbon.json` has the one favourable density (4.0) and
  already validates at 1.79 GiB/s — indistinguishable from the `nested` pattern that
  [json-validate.md](../benchmarks/json-validate.md) describes as near the memory-bandwidth limit.
- **Headroom, but above break-even.** The two slowest files sit at densities of 24.0 and 20.0,
  squarely in the band where the prototype measured a regression.

No corpus file is both slow enough to be worth optimising and sparse enough for the scanner to
help. Rejected 2026-07-25.

Two supporting findings reinforce this:

- **String skipping is dead on real input.** String bodies are 4.6% of corpus bytes and the longest
  string in the corpus is **51 bytes**, against the ~300 B regime where #130 measured its win. Only
  0.03% of strings reach even 32 bytes.
- **The escape machinery could never pay.** Escape density is **0.00 per KiB in all five files**.
  The odd-backslash-run mask is the most intricate primitive in the design and has no equivalent
  anywhere in this crate, yet it is *structurally required* — a single `\"` desynchronises the
  in-string mask for the rest of the document. On real input it is unrecoverable cost.

Note that whitespace fraction is a misleading proxy and was nearly mistaken for the answer:
`3d-ribbon.json` is 85% whitespace, but in runs of p50=19 / max=23 bytes, and **0.00% of whitespace
runs in the corpus reach 32 bytes** — no SIMD lane is ever filled by whitespace alone.

Full analysis: [benchmarks/json-validate.md § Shape analysis](../benchmarks/json-validate.md#shape-analysis-what-a-chunk-scanner-could-win-130).

## Consequences

- The validator remains scalar recursive descent. Its public API — `ValidationErrorKind`,
  `Position`, and the first-error semantics the CLI renders — is unchanged.
- **The optimisation with real headroom is the inverse of #130.** The slow files are slow because
  they are *token-dense*, so the win is in making per-token work cheaper (keyword and number
  scanning in the scalar path), not in skipping bytes between tokens. That work proceeds separately.
- The same density analysis constrains the adjacent SIMD proposals #122 and #123, which target the
  same validator.
- Extends the ADR-0007 lesson from input *size* to input *density*: a micro-benchmark win only
  translates when the benchmarked shape occurs in real workloads — and "shape" must be measured
  with the metric the optimisation is actually sensitive to. Whitespace fraction, the intuitive
  proxy here, points the opposite way from the truth.
- Neutral: this ADR records a *non*-implementation. If JSON workloads with sparse token density
  *and* headroom below the bandwidth ceiling become common, it can be revisited with fresh corpus
  data — the benchmark and corpus tooling built to answer this question is retained.
