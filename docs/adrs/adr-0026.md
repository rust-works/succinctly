# ADR-0026: Carry jq's Path Register in a Path-Mode Interpreter, Not Infer It (#5223)

## Status

✅ Accepted (2026-10-25). Supersedes the register model of
[jq-path-register-producer-contract.md](../plan/jq-path-register-producer-contract.md) (now
Archived) for the programs described below; [ADR-0018](adr-0018.md)'s fidelity rule is the reason,
and [ADR-0025](adr-0025.md)'s native-stack floor still bounds the new evaluator.

## Context

jq 1.7.1 tracks paths with a register in its VM: `path(f)` runs `f` with a `(path, value)` pair
that only navigation advances, and `INDEX`/`EACH`, `getpath` and `PATH_END` each compare the value
in hand with the register's using `jv_identical` (pointer identity for arrays, objects, strings and
literal numbers). Whether `path(E)` answers, and what it answers, therefore depends on which value
storage reached each check, through binds, folds, `?//` retries, `try`, `label` and every C builtin
that hands its input back.

succinctly's path resolver (`resolve_node_sink` and the fold drives in `src/jq/eval.rs`) never had
that register. It **inferred** one: a producer contract said, per construct, whether the register
moved, and where it could not prove an answer it refused loudly rather than risk a wrong write. Each
refinement of the inference closed some rows and left neighbours refused or wrong. The issue stream
did not converge: #4800, #5013, #5030, #5042, #5044, #5101, #5113, #5156, #5175, #5181, #5194,
#5203, #5205, #5207 and #5213 were all open or recently closed refinements of the same model when
#5223 was filed, and `docs/compliance/jq/limitations.md` carried dozens of refuse-only entries.

#5223's Phase 0 spike ([jq-path-mode-interpreter-spike.md](../plan/jq-path-mode-interpreter-spike.md))
built an interpreter over the parsed `Expr` that carries the register with every output, as jq's
bytecode does, and measured it against jq and against the shipped resolver over the repository's
differential sweeps. It matched jq on rows the resolver refused or answered wrongly, and lost none
the resolver matched. Phases 1 and 2 gave `OwnedValue` the identity jq's checks read (storage
identity for containers, promotion for strings and literals, a table of the C builtins that return
their input) and ran the interpreter in shadow beside the shipped route over the whole test suite.

## Decision

**A jq-mode program whose path target is dynamic runs whole through the path-mode interpreter
(`src/jq/path_mode.rs`) on the materialized document.** `path_mode::takes_program` decides it once
per program:

- *jq mode only* (`EvalTag::Jq`); yq keeps its own path model and walkers;
- *a dynamic path target*: an argument of `path`/`del`/`pick`, or the target of an assignment
  (`=`, `|=`, `op=`, `//=`), that is neither navigation (`.a`, `.[i]`, `.[$k]`, `.[a:b]`, `.[]`,
  `..`, `recurse`, `recurse(.[]?)` and pipes, commas, parentheses and `?` of them) nor a value
  filter over navigation (`try S`, `try S catch empty`, `first(S)`, `S // T`, and `select(c)` for a
  condition with no `?//`, function call or input). None of those moves the register off the
  navigated value, so the streaming walkers answer them as jq does; none of the 1,253 rows where
  the Phase 2 shadow found the shipped route wrong has such a target;
- *no declined construct*: no cursor-metadata builtin (`line`, `column`, `document_index`,
  `anchor`, `style`, the comment builtins, `at_offset`, `at_position`), no
  path-context builtin (`key`, `file_index`, `filename`), no yq-only syntax.

`eval_full`, the hidden entry that is the shipped evaluator alone (for the generic evaluator's
bridges and the parity tests), is not routed.

The interpreter carries jq's register `(path, value, subexp nest)` with each output and applies
`jv_identical` where jq does. Static targets keep the shipped walkers, which answer the same and
stream. A document the interpreter cannot materialize whole (a lone surrogate, nesting past the
materializer's 256 levels) stays on the shipped route, which decodes only what the program reads
(#4412) and walks deeper (#3850).

Writes run natively (`modify_native`/`assign_native`), as jq's `_modify` and `reduce path(f) as $p`
do, and fall back to jq's own `_modify` body from the prelude when a `?//` in the update or the
paths can retry into it. jq-defined builtins run their 1.7.1 `builtin.jq` bodies; C builtins run
natively or through the shipped evaluator, with the identity jq's C code gives their result.

## Consequences

**Positive**

- jq fidelity for these programs is a property of the evaluator, not of a growing inference: the
  superseded issues' rows all match jq 1.7.1, and the refusal pins the old resolver needed (test
  rows asserting "refused where jq answers") now hold jq's answers.
- The yq resolver, the static walkers and every value-mode route are untouched.

**Negative**

- The programs taken materialize the whole document, where the shipped resolver walked a cursor.
  Measured at merge, interleaved A/B against the base commit on a `users` document (1 MB and
  10 MB), on a 7950X (terminus) and, indicatively, a busy M-series laptop: the common write and
  path shapes that stay on the walkers (`del(.users[] | select(.score < 100))`,
  `(.users[] | select(...) | .score) |= . + 1`, `[path(.users[] | select(.active))]`,
  `[.users[] | path(try .age catch empty)]`) are unchanged within noise (-2.3% to +2.6%). The
  programs the interpreter takes cost more: `del(.users[] | .score as $y | select($y < 100))`
  +8% at 1 MB and +1% at 10 MB, `del(.users[] | first(.score as $s | select($s > 900)))` +18%
  at 1 MB and +10% at 10 MB on the 7950X. The route has a fixed cost too, parsing its prelude
  and setting up: 0.65 ms per process on the 7950X (1.73 ms against 1.08 ms for a trivial
  program on `null`), part of the 1 MB rows' 1.7 ms and 3.9 ms. Before the value filters were kept on the walkers,
  `path(try .age catch empty)` read +122% at 10 MB: the reason they are.
- The routing is syntactic and per program: one dynamic path target anywhere, even in a `def`
  that is never called, sends the whole program to the interpreter and materializes the
  document. Reachability is not decided.
- Two path evaluators remain in jq mode. The shipped resolver is still reached by the declined
  programs and by undecodable documents, so its register machinery cannot be deleted yet.
- Recorded divergences: a write to an unshared slice view builds a new array where jq writes the
  view in place and keeps its offset (so a later slice past 65,535 answers where jq refuses);
  `del(.[nan])` answers the document where jq loops forever; walks with no end raise the shipped
  caps (`recurse`, `range`, `until`/`while`, `repeat`) where jq never returns.

## Alternatives Considered

- **Keep refining the inferred register.** Rejected: every refinement was local, the issue stream
  did not converge, and each refusal cost an answer jq gives.
- **Run every jq program through the interpreter.** Rejected: value-mode and static-path programs
  gain nothing from the register and would lose the cursor routes' streaming and memory profile.
- **Interpret only inside `path(...)`.** Rejected: the register crosses pipes, binds and fold
  bodies around the path expression (`. as $x | ... | path($x)`), so the whole program has to
  carry it.
