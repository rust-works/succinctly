# ADR-0023: Module Scope Boundary as a Resolver Floor (#2951)

## Status

✅ Accepted (2026-09-16)

## Context

`succinctly jq` implements jq's module system by **AST inlining**: `ModuleLoader::process_program`
wraps every `include`d module's defs, then `~/.jq`'s, then every `import`ed module's
(namespaced) defs, around the main filter as one flat chain of `Expr::FuncDef` nodes. Each
wrap nests the previous expression one layer further in, which is what gives jq's
innermost-first resolution order for free (#2682, #2865).

The chain is also the problem. A module body physically sits nested *inside* every source
wrapped around it afterwards, so ordinary lexical scoping resolves outward into them —
and resolves names real jq keeps out. Real jq gives each module its own sealed scope.
Confirmed live against jq 1.7.1:

| fixtures | filter | jq 1.7.1 | succinctly, before |
|---|---|---|---|
| `~/.jq` = `def hj: 1234;`, `usehj` = `def uh: hj;` | `include "usehj"; uh` | `hj/0 is not defined at …/usehj.jq` | `1234` |
| `sibA` = `def sa: sb;`, `sibB` = `def sb: 77;` | `include "sibB"; include "sibA"; sa` | `sb/0 is not defined at …/sibA.jq` | `77` |
| same | `include "sibA"; include "sibB"; sa` | same error | error — but *by accident* |
| `sibA3` = `def sa3: b::sb;` | `import "sibB" as b; include "sibA3"; sa3` | `b::sb/0 is not defined` | `77` |

The third row is the tell. Reversing the two `include`s made succinctly agree with jq
because `sibB` was no longer wrapped outside `sibA`'s body — the right answer for the wrong
reason, which is leakage through the chain rather than a scoping rule.

One property, verified rather than assumed, bounds the blast radius of any fix. A module's
source is parsed by plain `jq::parse_program` with **no shadow-candidate seeding** (#2036,
and the flip side of #2950), so a call to a builtin inside a module body is never an
`Expr::FuncCall` and never consults the def chain at all. Confirmed live: with `sibDefLen`
= `def length: 99;` and `sibLen` = `def sl: length;`, both include orders answer `2` in
both tools. Therefore **a leaked name could only ever resolve where jq reports a compile
error; it could never out-shadow a name jq resolves.** Sealing the scope can turn a wrong
answer into a compile error. It cannot change a correct answer into anything else.

## Decision

**The boundary is encoded as marker defs in the chain, and enforced as a floor on scope
lookup in `resolve.rs`. Nothing else moves.**

1. **Markers.** The loader brackets every *run* of defs it wraps — each `include`, the
   `~/.jq` block, each `import` — between two `Expr::FuncDef` nodes with `Identity` bodies,
   named `<NUL>run:begin:<id>[:<alias>]` and `<NUL>run:end:<id>`. A NUL byte cannot be
   lexed, so no call written anywhere can ever name one. `ModuleRun` owns the spelling,
   shared by the loader that writes markers and the resolver that reads them.

2. **The floor.** Because markers are ordinary `FuncDef`s, both walks in `resolve.rs`
   already push them onto their scope stack and truncate them at the right moment — **no
   walk state is threaded through either recursive walk.** Only lookup changes, once, in
   `scan_scope`: scanning innermost-first, an end marker opens a *closed* run (wrapped
   around this point, so its defs are visible) and a begin marker with no matching end is
   the floor. Everything below the floor belongs to another module and is invisible.

3. **The import retry.** A bare `name/arity` that misses under the floor, while the
   innermost open run carries an alias, is retried as `alias::name` and the call renamed in
   place. This closes #2989 — a def inside an `import`ed module could not call its own
   sibling, because the loader namespaced the defs but not the call sites in their bodies.
   The retry lives in **both** walks, or reachability and checking would disagree about
   which bodies are compiled at all.

4. **Barrier runs, for authorship without visibility.** A module's *dependency* defs are
   spliced into its own def bodies, so a dependency's body is physically nested inside the
   importing module's run. Two things follow from that nesting which have nothing to do
   with which names are visible: the import alias would reach a body that has no right to
   it, and a compile error would be blamed on the enclosing module rather than the file
   that wrote the call. Both are wrong, and the first is *worse than the pre-boundary
   behaviour* — it turns a correct compile error into a wrong answer, the one direction
   the soundness argument below says cannot happen.

   So each dependency group is bracketed by a **barrier** run: it claims authorship (it is
   the innermost open run, so it owns the alias question and the error attribution) but
   does **not** floor visibility. Closing the visibility half is #2962's capture route, and
   doing it here would move two of that issue's pinned rows from a wrong answer to a
   compile error — still not jq's answer. Upgrading a barrier to a `Begin` is the whole of
   that later change.

   *Superseded by the #2962 amendment below: dependency groups are now ordinary flooring
   runs, and the barrier kind is gone.*

5. **The evaluator is untouched, and provably so.** The sealed window is a *suffix* of the
   very stack the evaluator's own innermost-first lookups walk. The nearest match within a
   suffix is the nearest match overall whenever one exists; when none exists, the program is
   a compile error and evaluation never starts. Combined with the builtin property above,
   there is no input on which the two could pick different defs.

6. **Attribution rides the diagnostic, not the AST.** `UnresolvedCall` gains `origin`, the
   innermost open run of *either* kind at the failing call — so a dependency body is
   attributed to its own file, not to whichever module encloses it — and the diagnostic
   names that canonical file as jq does instead of `<top-level>`.

### Amendment (#2962, implemented): dependency groups floor, and a clash is a rename

Decision 4 left each per-body dependency group visible to the def it is wrapped into. That
nesting is the whole of #2962: a dependency's body could see the def's own name, its
parameters and other origins' groups, none of which jq's separately bound module block can
see. Upgrading the barrier to a `Begin`, as decision 4 anticipated, closes that for calls.
Three further changes were needed to reach jq's answers rather than trade a wrong value for
a compile error, all confirmed against jq 1.7.1 over a 29-row fixture matrix
(`test_dependencies_are_bound_in_their_own_scope_2962`):

1. **Variables floor too.** A run marker is pushed onto the resolver's variable stack as
   well as its function stack, so `def h($g): k;` with a dependency `def k: $g;` is jq's
   `$g is not defined` at the dependency's file. `UnboundVar` gains the same `origin` as
   `UnresolvedCall`, and the reporter names the module's file, line and source for it.
2. **A clashing dependency is renamed, not excluded.** `visible_deps_for` used to exclude a
   dependency sharing the def's (name, arity), or named after one of its parameters, when
   the body called that name directly, since the wrap would otherwise shadow the def's own
   binding for the body. Under a floor that exclusion strands every *other* dependency that
   calls it: `def c: 7; def g: c;` included by `def c: if . == 0 then g else (. - 1 | c)
   end;` became a compile error where jq answers `7`. A clashing dependency that another
   dependency needs is now kept under a NUL-prefixed name (`ModuleRun::renamed_dep`), and
   the calls that reach it inside the group are renamed with it. The body's own calls to the
   name never counted towards keeping it, since they always bind to the def or parameter.
3. **The rename walk honours scope.** A call is renamed only where it resolves to the
   renamed entry: from that entry's own body and later entries, stopping at a later entry of
   the same (name, arity); not under a nested def of that name, or a parameter of that name
   at arity 0; and not inside a dependency's own nested runs, whose defs are floored from it
   but still shadow it after their end marker.

This is the name mangling rejected below, but used for a different job. Mangling fails as a
*boundary* because an exported name must stay callable bare. Here the floor is the boundary,
and the rename only moves an entry that the floor has already made private to its group out
of one def's way. `ModuleRun::display_name` maps the internal name back wherever a def's
name reaches a message (the recursion-depth error), so it never surfaces.

*Points 2 and 3 are superseded by the #2955 amendment below: dependency bodies are no
longer wrapped into the defs that reach them, so there is no clash to rename. Point 1 stands.*

### Amendment (#2955, implemented): a dependency module is linked once, and forwarded to

Binding a module's dependencies by **copying** their bodies into every def that reached them
compounded down a chain: each level's bodies already carried the level below, so a chain
whose defs each call `F` defs of the level below held `F^L` copies of the bottom one. The
issue's 14-level, fan-out-2 chain peaked at 681 MB against jq's 2 MB (release, correct
output throughout). The "symbolic binding at load time" listed under the alternatives below
is now taken, in a form that changes neither the marker representation nor the evaluator:

1. **One link run per dependency module.** A module some other module depends on is emitted
   **once**, as an ordinary run (`wrap_run`) placed outermost in `process_program` -- outside
   the imports, `~/.jq` and includes -- whose begin marker carries a hidden alias
   (`ModuleRun::link_alias`, `<NUL>link:<id>`) and whose defs are named
   `ModuleRun::link_name` (`<NUL>link:<id>::<name>`). Inside the run a bare sibling call
   misses those names, floors at the run's own marker, and is retried under the alias by the
   very code decision 3 added for `import`ed modules; the retry renames the call in place, so
   the evaluator binds it unchanged. From outside, nothing lexable spells a link name, so the
   run re-exports nothing. Error attribution reads the innermost open run as before, so a body
   error names the dependency's own file -- and, since the body now exists once, it is
   reported once (#3058, closed by this).
2. **Forwarding stubs in place of copies.** `load_and_bind_module` wraps each of a module's
   own def bodies in one stub per dependency (name, arity) the body calls directly --
   `def g(a; b): <NUL>link:<id>::g(a; b);` -- with the two exclusions the copying loader had
   (the def's own (name, arity), and a parameter's name at arity 0). A stub holds no lexable
   free name, no `$variable` and no `$__loc__`, so it needs no run and can capture nothing;
   the transitive closure and the rename above are therefore gone. Arguments forward as
   closures, and the dependency does its own `$param` binding on arrival.
3. **The one resolver change.** `scan_scope` steps over an open begin marker -- instead of
   stopping at it as the floor -- exactly when the name being looked up is a link name. A stub
   sits inside some run of its own and its target is outside every run. The two lookups that
   can meet a link name (`in_scope`, `reach_in_scope`) compute the flag from the name; variable,
   label and `enclosing_run` scans never cross.
4. **Placement decides compile-error order.** Link runs are wrapped in dependency post-order
   with each module's directives visited last-declared first (`ModuleLoader::hoist_order`), so
   `resolve::check` meets a dependency's bodies before its includer's, the last-declared
   dependency's first, and a chain's deepest first -- which is jq 1.7.1's order (captured live
   for all three shapes; the copying loader printed the includer's own errors first).
5. **Only what is referenced is linked.** jq's `block_bind_referenced` rule at the module
   level: a linked module emits a def only if a body reached by name from the main filter --
   through the top-level runs, then the linked modules dependents-first -- names it. Every
   chain def is installed over the whole program below it at evaluation, so chain length is
   the cost that matters; seeding from every top-level def instead cost 22 MB against 12 MB on
   a six-level, forty-def chain the filter walks one def of.

**Soundness, re-derived from decision 5.** A link run contains no bare-named def, so a bare
name the resolver accepts anywhere resolved to a def inner to every link run, which the
evaluator's innermost-first install also picks first. A link name exists only in its own run,
and same-name entries there are innermost-first in both passes. There is no input on which
the two pick different defs. The 30 rows of `test_dependencies_are_bound_in_their_own_scope_2962`
are unchanged.

**Measured** (this machine, release, `/usr/bin/time -l`, output identical to jq on every row):
the 8 x 6 x 3 chain 142 MB -> 34 MB, 12 x 4 x 2 162 MB -> 36 MB, 14 x 4 x 2 681 MB -> 112 MB
and 0.38 s -> 0.03 s; the flat 6 x 40 x 1 chain 12 MB -> 9 MB, and a 1000-def utility module
used for one function through two modules 9 MB -> 9 MB. The processed program's node count is now linear in chain depth
(`link_size_guard_2955`, which read 1253 / 5093 / 20453 nodes at 6 / 8 / 10 levels before).
What remains above jq's 2 MB is the evaluator's own: a `DefCall` node caches its bound body,
and a call tree of `F^L` calls leaves `F^L` cached copies behind, module or no module -- the
same 56 defs in one file cost 58 MB, and `fib(20)` 234 MB. That is a separate, pre-existing
evaluator issue, #3148.

**Hot path** (Apple M4 Pro, idle, interleaved, 25 reps, median): `[range(1e5) | f]` where `f`
calls one dependency through a stub moved +1.6% while the same defs written inline in one
program, which this change cannot touch, moved +3.3% -- neutral within the noise floor.

**The one shape that pays** (same box and method): a 20-module x 50-def chain of which the
filter uses one def starts in 9 ms against 20 ms before; the same chain with all 50 top-level
defs used, so that all 950 dependency defs are referenced and linked, starts in 136 ms against
32 ms. Every def in the top-level chain is installed over the
whole program below it when it is bound (`bind_def` rebuilds its `then`), so a chain of `M`
defs costs `O(M x N)` at startup; the copying loader kept those 950 bodies nested inside the
defs that used them, where each install was local. That quadratic is the evaluator's, and
pre-existing -- a single top-level `include` of 3000 defs costs 1 GB and 0.5 s today -- and it
is what the referenced closure above bounds by usage. It is filed with the retention issue, #3148.

## Alternatives rejected

- **A field on `Expr::FuncDef`.** Adding any field costs 8 bytes on *every* `Expr` — the
  discriminant stops riding a niche (measured for #2283) — and eats the `MAX_EXPR_DEPTH`
  stack margin, which has been the binding constraint before. Rejected on cost.
- **A side table keyed by node address.** `substitute_vars` rebuilds the tree between the
  loader and this pass, so no address recorded by the loader survives to be read. Rejected
  as unworkable, not merely expensive.
- **Name mangling** — rewrite each module's own defs and internal call sites to a
  per-module prefix. **Rejected as unsound**, which is the finding worth recording: it does
  not close the leak at all. An exported name must stay callable *bare* from the main
  filter, so its bare wrapper stays in the chain outside the sibling's body, and
  `def sa: sb;` still finds it. The only way mangling closes the leak is by rewriting the
  *callers* inside the sibling — which requires knowing `sb` is free there, i.e. the
  resolver's job. Mangling is a worse spelling of this ADR's decision, not a different one.
- **Symbolic binding at load time** (bind each module's defs to handles when loaded, rather
  than inlining an AST). This is the eventual answer to #2955's memory compounding and
  would make the boundary structural rather than marked. It is a far larger change to the
  loader and evaluator both, and is deliberately left as future work: nothing in this ADR
  blocks it, and the markers disappear with the chain if it ever lands. *Taken by the #2955
  amendment above, in a form that keeps the markers and leaves the evaluator untouched: the
  handle is a hidden name, and the binding is the alias retry the resolver already had.*
- **Splicing dependency bodies behind `Expr::Shared`** (#2955's own first suggestion).
  Unsound today on two counts: `resolve::check` un-shares a multi-owner `Rc` through
  `Rc::make_mut` (#2971), so the memory comes straight back at compile time, and a shared
  body's free names would resolve against whichever scope each splice site sits in, which is
  #2962's capture family again. Linking once and forwarding shares nothing and resolves each
  body in exactly one scope.

## Consequences

- Five leak shapes now match jq on exit code, error name, error count, ordering and module
  path. #2989 is closed as a by-product.
- The `~/.jq` block is sealed like any module, so its bodies cannot see an `include`d or
  `import`ed name either — matching jq.
- **Not applied to the per-body dependency runs** `load_and_bind_module` wraps. The same
  marker would also seal those, closing #2962's capture route, but it flips two of that
  issue's three pinned rows from a wrong *answer* to a compile *error* — still not jq's
  answer. Trading one divergence for another belongs in #2962's own PR, with its own
  decision about whether an error beats a wrong value. *(Since applied, with the renaming
  that avoids that trade: see the #2962 amendment.)*
- Cost is resolve-time only: two extra nodes per run, and a scope scan that already walked
  innermost-first now also counts markers as it goes. The scan stops at its match rather
  than continuing to find the enclosing run — `ScanResult::run` is documented as meaningful
  only on a miss — because scanning on regardless makes every lookup walk the whole stack,
  which is quadratic over a long def chain. Measured on chains of 3000 and 6000 defs
  (interleaved, 5 reps, median): parity with the pre-change binary.
- A module-body compile error still lacks jq's `, line N:` and source echo, which need the
  module's *text* threaded to the reporter (#2991). *(Closed by #2991 for calls, and by
  #2962 for variables.)*
