# ADR-0024: Structural Sharing in `OwnedValue` (#2999)

## Status

✅ Accepted (2026-09-17) — decided by the measurements in [Decision](#decision): B (#3000)
and C (#2999, PR #3074) both accepted on their numbers. G (#3009) is implemented and
measured on the 7950X and on an M5 Max standing in for the M4 Pro (see
[Option G result](#option-g-result-3009-measured-2026-09-18)); the M4 Pro leg is outstanding.

## Context

Every jq write route that must keep an *unmutated* document alongside a *written* one pays a
whole-tree copy of `OwnedValue` (`src/jq/value.rs`):

- `eval_assign_streaming` (`src/jq/eval.rs`) clones the pristine document before applying
  each write as its path resolves. The separation is jq's own and is observable
  (`.[(.a,.a)] = 5` on `{"a":"b","b":1}` must resolve the second `.a` against the unwritten
  document), so it cannot be dropped. #2976 measured it at **+18% peak RSS** on a 1.5 MB /
  200,000-element array (`.[(0,1)] = 0`: 74.8 MB → 88.5 MB). #2990 narrowed the set of
  shapes that pay it to genuinely multi-path ones; the residual is this ADR's subject.
- `fork_rhs_over_paths` clones the document once per right-hand-side output.
- `set_path`'s `Iterate` arm clones the new value once per slot, and the streaming write
  clones it once per path.
- `eval_update` would inherit the same cost if #2974 moves `|=` to a streaming write.

jq pays nothing for any of these because `jv` is refcounted and `jv_setpath` copies on
write. succinctly's `OwnedValue` owns its containers inline, so a "copy" is a deep copy.

Facts measured against the tree at `223360178` (2026-09-16), which every option below is
priced against:

| fact | value |
|---|---|
| `size_of::<OwnedValue>()` | **72** — `Object(IndexMap<String, Self>)` is the widest arm (`IndexMap` = 72; `Vec`/`String` = 24; `NumberRepr` = 16; `Box<str>` = 16) |
| same, with the object map boxed (`Object(Box<IndexMap<..>>)`) | **32** |
| same, with `Rc<Vec<Self>>` + `Rc<IndexMap<..>>` | **32** |
| same, with `Rc<str>` + `Rc<[Self]>` + `Rc<IndexMap<..>>` | **32** |
| construction sites | 875 `OwnedValue::Array(` + 543 `OwnedValue::Object(` across 11 files (`eval.rs` 928, `eval_generic.rs` 221, `yq_runner.rs` 85, `lazy.rs` 40, `value.rs` 31, `stream.rs` 28, five files ≤ 10) |
| by-value `mut` destructures of a container | 13 |
| `&mut` entry points | `as_array_mut`, `as_object_mut`; walkers `set_path`/`set_path_steps`, `update_path`/`update_path_steps`, `delete_at_path`/`delete_at_path_through_absent`, `autovivify_object`/`autovivify_array` |
| exact size pins that a 32-byte value trips | `eval_error_size_is_pinned_for_the_1021_stack_overflow_fix` (96), `eval_error_payload_is_no_larger_than_the_option_it_replaces` (`src/jq/error.rs`); `test_generic_result_size_stays_bounded_789` (120), `test_generic_item_size_stays_bounded_789` (80) (`src/jq/eval_generic.rs`) |
| thread boundary | `main` runs `run_main` on one big-stack thread; only `anyhow::Result<()>` crosses the join. No `Send`/`Sync` bound anywhere in `src/jq`; `jq_runner` never wraps an `EvalError` (which carries an `OwnedValue`) in `anyhow::Error` |
| existing precedent | `Expr::Shared(Rc<Self>)`, `Expr::TrackedVar(Rc<Tracked>)`; `PathNode::Owned(Rc<OwnedValue>)` and `WalkNode::Made(Rc<OwnedValue>)` already share a *whole* owned value by refcount — the containers inside it are what this ADR would share |
| serde | no impl on `OwnedValue`; the `serde` feature covers the bit structures |
| public API | `succinctly::jq::OwnedValue` is `pub` on crate 0.8.0; a payload change breaks downstream `Array(v)`/`Object(m)` patterns |

Two of those facts reshape the question the issue asked. All three boxed layouts measure
**32**, not the ~40 #2976 estimated: `NumberLiteral(NumberRepr, Box<str>)` becomes the
widest arm at exactly 32 and the discriminant packs into `NumberRepr`'s niche. That is
−55% per array element on *every* route, eager ones included — for the #2976 repro a
single copy drops from 14.4 MB to 6.4 MB before any sharing exists. And the size effect is
available *without* sharing (boxing the map alone), which means the two mechanisms can be
measured separately. They must be: an A/B of the `Rc` layout against the status quo would
attribute the size win to sharing.

## Decision

**The decision is made by measurement against four criteria, in the order below, and this
section is completed — not rewritten — when the numbers exist.** Until then the status quo
stands.

Options priced:

| | layout | size | sharing | cost | status |
|---|---|---|---|---|---|
| A | status quo | 72 | none | — | baseline |
| B | `Object(Box<IndexMap<..>>)` only | 32 | none | +1 allocation per object; +1 pointer chase per object access; per object 32 inline + 72 heap instead of 72 inline | **measured and accepted** (#3000 / PR #3004), see below |
| C | `Array(Rc<Vec<Self>>)` + `Object(Rc<IndexMap<..>>)` | 32 | containers | as B for both container kinds, +16 B refcount header, a refcount check on every `Rc::make_mut` | **measured** (PR #3074), see below |
| D | C + `String(Rc<str>)` / `Array(Rc<[Self]>)` | 32 | everything | as C; every string mutation (`+=`, `ltrimstr`, `ascii_downcase`, …) clones first; keys stay `String` regardless | deferred |
| E | `Arc` variants of C | 32 | containers | atomic refcounts for a thread boundary that does not exist | rejected |
| F | B (or C) with a small-object representation behind `ObjectMap` — linear entries below a threshold, `IndexMap` above | 32 | as B/C | one allocation per small object instead of three; every `IndexMap` method the crate calls must be provided instead of deref'd | **withdrawn** — priced against a regression that turned out to be option G's, see below |
| G | B + print an owned result directly instead of rebuilding it as `lazy::JqValue` | 32 | as B | none at the value layer; a printer-path change under a byte-identity contract | **measured** (#3009), see below — removes B's three residual rows |

Procedure:

1. **B first, as the mechanism holdout (#3000).** It realises 100% of the size drop and 0%
   of the sharing, so its result is C's floor: both carry the same pointer chase. If B loses
   on time where the change is charged to every input — arrays of many small objects, where
   allocation count rises — C starts from that loss and must buy it back with the copies it
   removes.
2. **C, built on B.** `Rc::make_mut` at the `&mut` entry points listed above; the
   whole-document clones in `eval_assign_streaming` and `fork_rhs_over_paths` become a
   refcount bump per shared subtree. The risk class #2976 named — a by-value destructure
   that silently lands in the clone arm — is instrumented directly rather than left to an
   A/B: a test-only counter on every `Rc::try_unwrap`-fell-into-clone and
   `make_mut`-had-to-clone site, run over the test suite and the bench queries, listing
   every site that cloned where a unique refcount was expected.
3. **Accept C only if all four hold**, measured on an Apple M4 Pro and an AMD Ryzen 9 7950X
   with the interleaved method in `docs/guides/benchmarking.md` (both binaries alternate
   within each repetition; a never-triggering holdout build measures the layout bias and is
   subtracted; inputs ≥ 1 MB at two sizes; the machine verified idle):
   - **Output identity** on every A/B input in both modes, before any number is read.
   - **Peak RSS and wall time** across `jq_bench`, `yq_bench`, the perf-guard matrix, the
     #2976 shapes (`.[(0,1)] = 0`, `.[$k] = 0`, `.[0] = 0`, `del(.[(0,1)])`,
     `.[(0,1)] |= 0`) and a small-objects array shape (the allocation-count worst case):
     no shape regresses beyond the holdout's own band, and the multi-path shapes lose their
     second copy.
   - **perf-guard green on both CI architectures** with no per-query threshold override
     for a regression. The guard is `abs(drift)`, so a row that *improves* past its band
     fails too; such a row takes the guard's documented override-with-removal-note (the
     #2878 procedure, #2963) and a follow-up issue to remove it once `main` carries the
     change.
     The rows that reach `OwnedValue` today are `users_assign_scores`, `users_del_select`,
     `users_del_bound_select`, `users_path_walk`, `users_yq_del_select`; the identity rows
     move ±5% from code layout alone and are read against the holdout.
   - **The clone list from step 2 is empty**, or every entry is explained on the PR.
4. **Size pins are re-derived, never bumped.** Each pin's comment states what it guards
   (#1021's controlled panic before a stack overflow; #789's per-push cost). The new number
   carries the same justification, and `into_owned_panics_past_nesting_depth_limit_1021`
   must still pass.
5. **The public-API break is recorded**, as a breaking CHANGELOG entry for the next 0.x
   minor, with construction and access still possible through constructors and accessors.

### Experiment B result (PR #3004, measured 2026-09-16)

Three release binaries (merge-base `223360178`, head, and a holdout built from the branch
with the `unboxed-object-map` feature restoring the 72-byte layout), interleaved with
`scripts/ab-cli.py`, output identity gated on every configuration with zero differences,
peak RSS as the minimum of five interleaved runs. Holdout RSS was flat against base on every
row (within ±0.8%), so the deltas are the layout change.

**The first measurement mis-attributed its one regression, and the correction is the finding
worth recording.** With only `OwnedValue` boxed, `to_entries` on a 10 MB object read +25% to
+41% peak RSS on both chips, and the implementer read it as "one allocation per small
object". DHAT showed head holding **15% less live heap at its peak** (454 MB vs 533 MB) with
23% more RSS: the extra memory was allocator holes. `succinctly jq` prints a materialised
result by rebuilding it as `lazy::JqValue` (`JqValue::try_from_owned`), object by object,
freeing each source map and allocating the destination one. While both enums were 72 bytes
the freed and requested chunk sizes were identical and the allocator recycled every chunk;
shrinking one side alone left ~290 bytes of holes per entry. Boxing `JqValue`'s map the same
way recovered most of it. `JqValue` cannot reach 32 — its cursor arm is 32 bytes with no
spare niche, so it is 40 — and the entries buffers still step one allocator bin during the
rebuild. That residual is option G's (#3009), not the layout's — and G has since removed it
(below).

| shape (peak RSS vs base) | Apple M4 Pro | AMD 7950X |
|---|---|---|
| 200k ints, `.[$k] = 0` | −25.9% | −31.6% |
| 2M ints, `.[(0,1)] = 0` | −38.0% | −34.5% |
| 2M ints, `sort_by(.)` | −44.0% | −41.5% |
| 10 MB `wide`, `map(.)` | −20.9% | −21.4% |
| 10 MB `wide`, `[.[] \| {k: .}]` | −4.2% | −7.0% |
| 10 MB 3-key objects, `[.[] \| {k: .a}]` | −9.1% | −6.4% |
| **10 MB `wide`, `to_entries`** | **+11.8%** | **+6.7%** |
| **10 MB `users`, `to_entries`** | **+20.2%** | **+23.4%** |
| **10 MB `users`, `[., .]`** | **+20.0%** | **+22.9%** |
| never-touching rows (`.`, `keys_unsorted`) | ≤ ±0.1% | +1.9% / +5.5% |

Wall clock, net of the holdout: the winning rows −6.9% (M4 Pro) and −17.5% (7950X) as a
group; object materialisation +1.5% / −2.0%; `to_entries` on a 10 MB wide object +4.6% /
+13.8% — the print-path rebuild again. perf-guard was green on both CI architectures with no
override.

**Decision on B (2026-09-16): merged, with the three residual rows recorded.** The
no-shape-regresses criterion is applied to the *layout*, and the layout regresses nothing:
every residual row is the print path rebuilding an owned tree, which #3009 removes. The
72→32 win is realised on every route and is no longer C's to claim; C inherits B's
per-container allocation and wins only where sharing removes a *copy*.

### Experiment C result (PR #3074, measured 2026-09-17)

**The mechanism.** `ArrayOf<V>`/`ObjectMapOf<V>` (`src/jq/value.rs`) hold
`Rc<Vec<V>>`/`Rc<IndexMap<..>>`; `OwnedValue::clone()` is a refcount bump per container and
the wrappers' `DerefMut` runs `Rc::make_mut`, so a write copies exactly the container it
goes through. Both enums keep using the same `ObjectMapOf`, so the conversion on the print
path frees and allocates matching chunk sizes (B's DHAT lesson). Every `&mut` and by-value
path is `#[track_caller]`, and `jq::share_stats` records each forced copy with the call site
that forced it -- which turned criterion 4 from an A/B inference into a list.

Pinned by count, not inferred from timings (`jq::eval::share_audit_2999`), over a
1,000-element document: `.[0] = 0` copies nothing; `.[(0,1)] = 0` and `.[(0,1)] |= 0` copy
the one `Vec` of element handles, once; N right-hand outputs cost N − 1 spine copies;
`del(.[(0,1)])` and reads through a binding copy nothing; `.[(0,1)].a = 1` over 1,000
objects copies the array of handles and exactly the two objects written.

**The audit (criterion 4).** Over the full lib suite (3,863 tests), the bin suite and 991
CLI queries over corpus-shaped inputs in both modes, every recorded site is one of three
things. *Fixed:* `navigate_static_component`, the destructive static-tail walk #2058 added
when a clone was a deep copy, swap-removed the child out of a container it held by value,
which on a shared container copied the whole container to extract one child. It is gone:
`value_after_components` now borrows and walks `WalkNode`s the way `path()` already did and
clones only the leaf it returns, a refcount bump for a container. And the
sort family wrapped every `[f]` key in an `OwnedValue::Array` it never shared -- not a
forced copy, but the one place the extra allocation per *array* showed (+6% to +27% on
`sort_by(.)`, +13% to +31% peak RSS, on both chips), gone once the keys are bare `Vec`s in
both evaluators. *The write itself:* the `set_path`/`update_path`/`set_value_at_path` arms,
one container per write, spine only. *An operand consumed to build a new value:* `+` and
`*` on containers, `error(v)`'s payload, and `JqValue::try_from_owned` printing a result
whose subtree is still held elsewhere (`.[(0,1)] = (1,2)`'s two documents,
`try error catch .`). Each of the last class was a deep copy made *earlier* before C; it is
now made once, lazily, and the print-path entries are the ones option G (#3009) removes.

**The holdout had to be corrected once.** Its first form held arrays behind a `Box` -- one
allocation more than #3000's inline `Vec`, a third layout rather than B's -- and it showed
the same `sort_by` regression as the shipped build, which is how the sort-family finding was
attributed. It now holds the array's `Vec` inline (24 bytes; the value stays 32), pinned, and
reads within ±3% of BASE on every wall-clock row and within ±1% on every RSS row on the
7950X. On macOS the holdout's RSS still moves ±5% on rows it cannot functionally change, so
the M4 Pro RSS deltas below are read against the holdout, not BASE.

**What sharing leaves.** For an array of scalars the spine *is* the array (a scalar has no
sharing granularity, and a number keeps its own boxed spelling), so the 200,000-int repro
still pays one copy of it: `.[(0,1)] = 0` is −14%/−17.5% but stays +28%/+26% above
`.[$k] = 0`, where B left +31%/+29%. For an array of containers the spine is the array of
handles and the gap closes: on 10 MB of three-key objects the multi-path write costs what
the single-path one does. Option D (shared strings) is what would close the rest.

**The costs that remain are the 16-byte refcount header per container**, +1% to +4% peak
RSS wherever a result holds many small containers (`to_entries`, a write into every element),
and one allocation per *array* -- B's per-object one, now for arrays too -- wherever a query
builds many small arrays it never shares: `[.[] | [.a, .b]]` on 10 MB of objects is +9%
peak RSS (7950X; the holdout +0.4%), the per-emitted-path array of `paths`/`tostream`/
`path()` is +1.7%/+2.3% instructions on the `users_path_walk` guard row, and `sort_by(.)` on
10 MB of 5-int arrays is the worst case (
+13.2%/+11.8% wall clock, +6.5% (-0.0%) / +6.8% (+0.3%) peak RSS). The never-touching rows and the yq DOM path are flat.

Cachegrind on the 7950X (instruction counts, deterministic, `--cache-sim=no`) puts the
residual where the RSS table does: HEAD executes *fewer* instructions than BASE on every
row -- `sort_by(.)` −2.1% on 200k ints and −2.0% on 1 MB of 5-int arrays, `map(.)` flat,
`.[(0,1)] = 0` −12.3% and −17.2% -- so the arrays-of-arrays `sort_by` wall-clock loss is
memory behaviour (one allocation per element array, a pointer chase per comparison), not
work. The holdout's counts sit within 1.6% of BASE.

**Decision on C (2026-09-17): Accepted, with the residual named.** All four criteria hold:
output identity on every configuration in both modes; every multi-path write shape smaller
and faster on both chips with the second document gone for arrays of containers; perf-guard
with no regression on any row on either CI architecture -- three rows *improved* past the
5% band (`users_del_select`/`users_del_bound_select` −13.2%/−11.3% and `users_yq_del_select`
−6.5%/−4.9% instructions on ARM64/x86_64), which the guard fails by design and which are
accepted through its documented override-with-removal-note, the same procedure #2878 used
for a faster row; and the clone list explained entry by entry, two of its entries fixed in
the PR. The one shape outside the holdout's band --
`sort_by(.)` on arrays of arrays -- is the per-array allocation that B's per-object one
already accepted, bounded and recorded here rather than hidden. Option D (shared strings)
stays deferred with its own number to beat: the spine copy of an array of scalars.

Decision outcome: B accepted; **C accepted** (above); **G implemented and measured on one
chip** (below), pending confirmation on the pinned machines.

### Option G result (#3009, measured 2026-09-18)

**The mechanism.** `GenericResult::Owned`/`ManyOwned`/`Partial` and the sorted-`keys` arm hand
`jq_runner` a finished `OwnedValue`; printing one ran it through `JqValue::try_from_owned`
first. A new `OutputItem` carries each result in the representation the evaluator already had,
and `print_owned_json`/`write_output_owned_value` print the owned shape directly. Under
`-S`/`-C`/`-a` the old route was worst — it converted an owned tree into a `JqValue` only for
`try_materialize` to convert it straight back — so that branch now hands `format_json` the value
it already holds. B's residual rows are the ones this removes.

Deliberately not a `JqValue::Owned` variant, though that is the smaller diff: `JqValue` is `pub`,
matched across nine files, and `lazy.rs` alone answers ~19 questions about it through `_ =>`
wildcards. `is_truthy`'s `_ => true` would be a wrong `-e` exit code for an owned `null` and
`as_str`'s `_ => None` would silently drop `-r` — a print-path optimisation must not be able to
move `-r`/`-e` semantics at all.

**Byte identity is the contract, and it is tested as one.**
`write_output_owned_value_matches_rebuilt_route_3009` asserts byte *and* error equality against
the rebuild route over ~160 values x 512 output configurations, so `try_from_owned` stays in the
crate as its oracle. It was negative-tested against three injected faults, including the exact
`NumberRepr` dispatch that makes `src/jq/stream.rs`'s owned writer print `null` for `1e400` —
which is why that existing streamer could not simply be reused here. Separately, 1680
succinctly-vs-jq-1.7.1 cases over the moved shapes and 15 flag combinations match exactly.

**Numbers** (release `cgu1+fat`, interleaved within each repetition, minimum of 9, outputs
gated identical before any timing; peak RSS from `/usr/bin/time -l` on macOS and `-v` on Linux;
baseline is the commit this branch sits on). Each cell is **peak RSS / wall clock**. The Apple
M4 Pro and the AMD Ryzen 9 7950X are this repo's two pinned benchmark machines; the M5 Max is
the dev laptop, included because it was measured first and because a second Apple part is what
separates "allocator" from "this one machine":

| shape (10 MB inputs) | M4 Pro | 7950X | M5 Max |
|---|---|---|---|
| `wide`, `to_entries` | −20.7% / −21.6% | −14.7% / −19.6% | −29.3% / −22.0% |
| `users`, `.users \| to_entries` | −41.5% / −17.8% | −23.2% / −30.5% | −39.9% / −19.2% |
| `users`, `[., .]` | −42.1% / −17.4% | −31.7% / −26.4% | −39.2% / −17.7% |
| `wide`, `keys` (sorted) | −14.7% / −7.7% | −27.4% / −12.1% | −14.5% / −7.1% |
| 200k ints, `.[$k] = 0` | −24.1% / −5.8% | **−1.0%** / −9.0% | −19.0% / −3.3% |
| 200k ints, `.[(0,1)] = 0` | −8.8% / −3.7% | **+0.3%** / −8.9% | −18.2% / — |

**All three agree on the win; they disagree on where it lands, and that is the finding.** Every
targeted row improves everywhere. But the two Apple parts give up resident memory where the
7950X gives up time — clearest on the write rows, which shed 9-24% RSS on macOS and *nothing* on
glibc (−1.0% / +0.3%) while still gaining ~9% wall clock there. The rebuild's free/alloc size
mismatch leaves holes in libmalloc's size classes that glibc's allocator does not leave. Two
Apple parts agreeing with each other and differing from glibc is what makes this an allocator
property rather than one machine's quirk. CLAUDE.md's rule, restated: a memory-bound effect does
not port across architectures. (`.[(0,1)] = 0` on *2M* ints read −7.0% on one M5 Max run and
+0.0% on another; it is noise, not a number, and is omitted.)

**The controls are what make the attribution, and they hold on all three.** `to_entries |
length` builds the identical owned tree and prints only a number: **+0.0% RSS** on the M4 Pro,
**−0.0%** on the 7950X, **+0.0%** on the M5 Max. So the tree still costs exactly what it did and
only its *printing* changed — the discriminator #3009 asked for. Identity, `map(.)` and
`sort_by(.id)` sit within ±0.8% RSS on every chip (±0.0% on the M4 Pro), as expected: all three
take the `LazySeq` route, which this change does not touch.

**The instruction-count guard confirms it independently.** `scripts/perf-guard.py` on the 7950X,
head against a merge-base binary built in the same run (`--baseline-binary`, #1582, so drift
shared by both cancels), moves exactly three rows: `users_assign_scores` −6.2%,
`users_del_select` −5.5% and `users_del_bound_select` −5.4%. All three are write/`del` shapes,
which produce an owned document and then print it. `arrays_map_iterate` — the `LazySeq` route —
is flat at −0.3%, and every identity/keys/path row is +0.0%. The guard fails on drift in either
direction, so this *improvement* fails it, and **what makes the gate pass is a
`QUERY_THRESHOLDS` override, not a baseline refresh**. On every PR and push run the guard
compares against a merge-base binary built in the same run and never consults the checked-in
file, so no edit to that file can move a PR's result. `users_assign_scores` gets a 12% entry
(the same size #2720 took for a move of this size), sized from CI's own measured delta —
−6.3% x86_64, −6.4% ARM64-Linux — with a removal note, tracked by #3161. The two `del` rows
also move past the 5% default (−5.6% / −5.5%) and pass only because #2999's 20% entries still
cover them, which couples their removal: #3077 must not drop those two until `main` carries
this change as well.

The checked-in baselines are refreshed too, following #2720's precedent, so a local `--check`
without `--baseline-binary` stays accurate — but that is hygiene, not the fix. The `x86_64`
half was measured on the 7950X; the `ARM64-Linux` half in an `ubuntu:24.04` aarch64 container on
the M4 Pro, where it reproduced the x86 result independently (the same three rows, −6.4% /
−5.6% / −5.4%) and landed within 0.8% of the checked-in CI-measured values on every untouched
row.

This also narrows [#3157](https://github.com/rust-works/succinctly/issues/3157), which was filed
believing the owned print path had no guard row at all: those three write rows do cover it,
indirectly. A `to_entries` row is still worth adding, because the shape the change was actually
aimed at — a large owned tree of *small objects* — is the one no row exercises.

**Review follow-up (same PR).** Three changes landed on top, and the third was load-bearing.
The container skeleton — the `len == 0` case, the compact branch and the pretty branch's
comma/separator/indent placement — is now one `write_json_container` shared by both printers
instead of four near-identical copies. `write_output` was merged into `write_output_owned_value`,
so the eager `-n`/`--slurp`/DSV route takes the streaming fast path too rather than always
formatting through `format_json`.

That merge exposed a divergence the first cut had deliberately parked. `--indent 0` sets an empty
indent with `compact` false; `format_json` keyed compactness off `indent.is_empty()` and printed
compactly, matching jq 1.7.1, while both streaming printers keyed it off `config.compact` alone
and emitted newlines with zero-width indents. While each route had its own writer this was
dormant and lazy-route-only; merging them would have carried the *wrong* spelling onto the route
that was right. Both printers now key off the indent string too, which settles it in the
reference's favour (ADR-0018) and closes the pre-existing lazy-route divergence as well. It is a
deliberate, user-visible output change — the only one in this work — pinned by
`test_indent_zero_is_compact_on_every_route_3155` (#3155) across all four routes, and the
printers' config sweep now covers the `("", false)` shape it had been excluding.

The merge also moved the eager route off a depth check that had been implicit. `format_json`
built the whole string before writing, so an over-deep value there panicked with nothing on
stdout; `print_owned_json` refuses only after 384 levels of `[` are written, which is why the
lazy route checks `check_tree_depth` in `to_jq_values` first. The eager route now runs the same
check in `evaluate_input_streaming`, so both routes report such a value at exit 5, print none of
it and carry on (`test_eager_over_depth_value_reports_cleanly_3155`). That also retires the
`-S`/`-C`/`-a` panic the eager route still had.

Every number in the table above predates these three changes, and the one re-measurement after
them was on the M5 Max alone (neither pinned machine had been reached at that point): it read
−29.4% / −39.3% / −42.1% / −14.6% against −29.3% / −39.9% / −39.2% / −14.5% before — unchanged
within this harness's noise — and `to_entries | length` stayed at +0.0%. The M4 Pro and 7950X
columns, and the instruction-count run, were all taken on the pre-review tree and have not been
repeated; the changes here are a printer refactor and a flag fix, neither of which touches the
allocation behaviour those numbers measure.

**Still open:** removing the `users_assign_scores` override once `main` carries this change
(#3161), in step with #3077's removal of the two `del` entries.

### Amendment (#2889, adopted 2026-09-19): node identity for owned values

This ADR's `Rc`-backed containers made `OwnedValue::Array`/`Object` copy-on-write
(`shared_container!`'s `DerefMut` via `Rc::make_mut`), but said nothing about *reusing* a
clone's `Rc` to answer a question the decision never posed: is this owned value the *same
node* jq's own `jv_identical` would call it? [#2642](https://github.com/rust-works/succinctly/issues/2642)
and [#3036](https://github.com/rust-works/succinctly/issues/3036) closed the fabricating
direction (an owned value wrongly treated as a node it is not) by demoting on every
funnel/re-entry; the accepting direction — a handful of shapes jq keeps the exact same `jv`
through (`{k:.} | .k`, `. + {}`, a fold returning its accumulator, `[.] | add|min|max` of one
element, …) that still refused here — was left as a documented residual, because nothing
before this ADR gave two `OwnedValue`s a way to *be* the same storage rather than merely
compare equal.

**The decision: derive `jv_identical` from `Rc` storage identity via a bind-scoped table,
not a per-constructor allowlist.** This is the issue's triage-plan option A (pointer identity
under this ADR's Experiment C), chosen over its option B (explicit embed provenance in both
evaluators). Option B would have taught each embedding construction (`{k:.}`, `. + {}`, `add`, …) to special-case
"my operand came from an unrebuilt bind" and thread that fact through its own return value —
one allowlist entry per jq builtin or operator that happens to preserve a `jv`, open-ended and
liable to miss a shape (a future builtin that also passes an operand through unchanged gets
nothing for free). Option A instead reads the fact `Rc` already encodes:
`eval_generic::embed_table` records, for the dynamic extent of a bind's body, the `(node,
document)` pair a `BindOrigin::Node` bind froze its value from, keyed to that value's own
`Rc`. `eval_generic::to_owned_cursor` (and `eval.rs`'s `to_owned`) consults the table at its
depth-0 entry, for a container cursor, before walking the node and reuses the bind's `Rc`
instead — so *every* construction
that merely re-reads the same node, present or future, shares storage with it automatically,
with no per-site allowlist to maintain. `RootWitness::of_owned` (jq mode only, `src/jq/eval.rs`)
then looks an owned root's storage up in the table at each funnel/re-entry to recover a `Node`
witness where the pre-#2889 code always saw `Owned`, and the existing `Node`/`Node`
certification (#2642) and `marker_is_root` promotion (#3037) do the rest unchanged — this
amendment adds a witness source, not a new comparison rule.

**Why pointer identity is sound here, and only here.** jq's own `jv_identical` *is* pointer
equality on a refcounted `jv`; deriving it from `Rc::ptr_eq` (`OwnedValue::shares_storage_with`,
`src/jq/value.rs`) is not an approximation of that rule but a restatement of it in this crate's
allocator. It is sound only because the bind holding the table's entry keeps a *strong*
reference for the entry's whole lifetime: a write through *any* handle to that storage —
including the bind's own, `$x.a = 9` — hits `Rc::make_mut`'s "am I the only owner" check
and finds it is not, so it copies before mutating. That is exactly the condition under which
jq's own copy-on-write fires (its refcount is also > 1 while `$x` holds a reference), and it
is why the write direction needed no separate proof: `{k:.} | .k | ($x.a) = 9` writes because
the copy happens first, and `{k:.} | .k | .b = 2 | path($x)` still refuses because the write
severs the sharing before `path($x)` ever runs.

That soundness is scoped tightly, on purpose:

- **Only within the bind's dynamic extent.** The table entry is a RAII guard pushed around
  `each_as_generic`'s evaluation of the bind's body and popped (truncated) on return, so a
  node id can never outlive the document it was minted from, and a *different* document
  reusing the same node id (impossible today, since ids are per-document, but the guard makes
  it structurally true rather than assumed) could not collide with a stale entry.
- **The witness is taken before re-entry, never across a write.** This is the same
  `ptr_eq`-across-a-mutating-walk caveat this ADR already carries for `Rc::ptr_eq` on the
  `unshared-containers` holdout: identity taken *before* a mutation and reused *after* it is
  unsound the instant the mutation triggers `Rc::make_mut`'s copy, because the old pointer no
  longer names the live value. `embed_table::witness_of` is called once per funnel/re-entry,
  freshly, against the value in hand at that moment — never cached across a step that could
  have copied-on-write in between.
- **Scalars stay out of the table entirely, by construction, not by a gap.** `OwnedValue::String`
  and the numeric variants are not `Rc`-backed (this ADR's own layout decision), so
  `embed_table::push` only ever holds `Array`/`Object` values and `shares_storage_with`
  returns `false` for every other pair. A scalar embed (`{k:.} | .k | path($x)` on `"s"`/`5`)
  stays refuse-only — not a smaller version of this mechanism, but a case it structurally
  cannot reach. Recovering it (this ADR's deferred option D: give scalars a node-identity proxy of
  their own) was deferred rather than folded in here, since it needs its own storage decision,
  not a reuse of the container `Rc` this amendment already had.
- **`no_std` and yq mode are the two scoping gates this ADR's own layout decisions already
  implied.** `embed_table` is a thread-local (`std`-only, like `file_index`); without `std` its
  functions are no-ops and every embed stays refuse-only, the same shape as every other
  `std`-gated witness in this crate. `RootWitness::of_owned` is gated on `S::TAG ==
  EvalTag::Jq`: yq mode keeps seeing `Owned` unconditionally, so its output is byte-identical
  to before this amendment — real yq's own node model (parent pointers, anchors, style) is
  [#2643](https://github.com/rust-works/succinctly/issues/2643)'s business, not this one's, per
  [ADR-0018](adr-0018.md)'s mode-decides rule.

**Stage B extends the same table to `eval.rs`'s own bind sites.** `eval_as`/`each_as` used to
call a bare, node-less `substitute_bound_var`, so a bind made on the `-n 'input | ...'`
route (`eval.rs`'s own input-queue bridge, not the generic evaluator) pushed no entry at
all and every embed on that route stayed refuse-only regardless of the table above. Stage B
mints a `BindOrigin::Node` from the bind source's own `StandardJson` cursor when one is
available (`eval::standard_json_bind_origin`, `substitute_bound_var_from` — the bare
spelling had no callers left once this landed, and was removed) and pushes the identical
entry `each_as_generic` already does, recovering the embed on that route without a second
mechanism. Three residuals remain there, all a consequence of what a `StandardJson` value
can still tell you after the fact rather than of the table itself: an empty container
retains no child cursor to recover its own node from; a further re-entry between the embed
and the read (collecting into an array, or a `getpath([])` in between) carries no witness
across it; and a navigated bind with no owned re-entry between the bind and the use at all
sits outside this mechanism entirely, unchanged by Stage B.

**Perf**, interleaved A/B on 2 MB and 10 MB `users`/`wide` corpora (identity gate, 0 diffs),
Apple M4 Pro and AMD 7950X: the embed shapes that used to pay for a second materialization
of the same node (`. as $x | {k:.} | .k`, `. as $x | . + {}`, `.[] | . as $r | {k:.} |
.k`) came out 30-57% faster on both chips; every shape with no `as` binding, and every
scalar-bind shape, stayed inside the control run's noise floor.

**Identity below the root (#3177).** The witness above is taken at a re-entry's *root*, so
an embed at a nested position of a rebuilt container — `[.] | path(.[0] | $x)`, where jq
answers the navigated `[0]` — could not be witnessed by it, and a positional marker
(`Origin::SnapshotAt`) cannot express it either, since `Frame::certifies` admits that origin
by value. The same storage identity is now also read where the resolver stands:
`marker_identical` certifies a marker whose value shares the container storage of the node
under the register, whatever the marker's origin. That is `jv_identical` itself rather than
a witness of it, and it is sound for the reason the table entry is: the marker's own strong
reference forces every write through any other handle to copy first. The resolver only
holds that pointer when an owned re-entry hands it the caller's own `OwnedValue`, so a
`path(f)`-headed re-entry now takes `owned_path_door` — the same reindex-free route the
generic evaluator's cursor-side `path()` arm always took, folded into one shared helper
(`path_over_owned`) — instead of the serialize-and-reindex bridge. jq mode only, as above;
the `del`/assignment resolvers and a `path()` reached through a wrapper still bridge
(#3188, #3189).

See [docs/compliance/jq/limitations.md](../compliance/jq/limitations.md)'s #2642 paragraph for
the user-facing table of recovered shapes and the residuals that remain refuse-only, and
[docs/plan/jq-bind-origin-frame.md](../plan/jq-bind-origin-frame.md) for the design note this
issue's mechanism was checked against.

## Alternatives rejected

- **Dry-run every write against the pristine document and apply them all at the end.**
  Unsound: write N's validity depends on writes 1..N−1. `null | .[("a",0)] = 1` vivifies an
  object at `.["a"]` and then fails at `.[0]`; against pristine `null`, `.[0]` would vivify
  an array and succeed. Same class as #2608's verify-then-echo.
- **Resolve the path generator against the semi-index cursor instead of a copy.** Closed by
  the resolver's signature: `resolve_node_sink` takes `&OwnedValue` and every `PathBranch`
  borrows it, so both documents must be owned trees for the whole loop.
- **Copy only the write's spine, without sharing.** The 200,000-element `Vec` *is* the
  spine; without element sharing its clone is the whole cost.
- **`Arc` (option E).** Nothing crosses a thread. Rejected on the facts above, not on
  taste; revisit only if a thread boundary appears.
- **An `Inline(Vec) | Shared(Rc<Vec>)` array representation, promoted on first clone.** It
  would remove the per-array allocation the residual above is made of, at the price of the
  32-byte value: a `Vec` is 24 bytes and needs a tag beside it, so `OwnedValue` would be 40
  and give back a fifth of B's win on every row. Not measured here; it is the trade a
  follow-up would have to state and price, the same way B and C were.
- **Sharing strings and slices too (option D).** Deferred, not rejected: strings are
  mutated in place by several builtins, keys are `String` either way, and D adds nothing to
  the copies this ADR exists to remove. It can be a later amendment with its own numbers.

## Consequences

Expected, to be confirmed or corrected by the measurements:

- `.[(0,1)] = 0` on the #2976 repro: 88.5 MB → ≈ 57 MB, matching `.[$k] = 0`; every
  eager-route row shrinks by the per-element factor whether or not C lands.
- Arrays of many small objects gain one allocation per object under B and one per
  container under C. B measured that cost at +5% to +8% of blocks, not of RSS: the RSS
  regression it first appeared as was the print-path rebuild (option G), and the same
  construction done explicitly (`[.[] | {k: .}]`) got cheaper.
- **A value-layout change must reach every same-shaped twin on a conversion path in the same
  PR** (`lazy::JqValue`; the tagged-object enum in `eval_generic.rs`), and the twins' sizes
  are pinned together. An RSS regression whose live heap is *lower* under DHAT is allocator
  state, not program data, and is attributed by free/alloc size pairing.
- `identical` (#1360) can gain an `Rc::ptr_eq` fast path for *reads* under C. It is not
  sound across a mutating walk — the streaming write is one — and is a separate change.
- `EvalError` shrinks with `OwnedValue` (its payload rides `Option<OwnedValue>`), which is
  the safe direction for #1021 but still moves an exact pin.
- Downstream users of `succinctly::jq::OwnedValue` who match on `Array(v)`/`Object(m)`
  must change with the next 0.x minor.
- The `docs/compliance/jq/limitations.md` residual paragraph for `.[(0,1)] = 0` points at
  #2999 until C lands or this ADR is marked Rejected with the numbers that rejected it.
