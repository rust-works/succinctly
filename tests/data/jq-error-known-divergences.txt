# Known divergences of succinctly's evaluator error wording from the pinned jq.
#
# Consumed by tests/jq_error_message_tests.rs. One line per diverging probe:
#
#   <probe>           <category>        <reason — #issue>
#
# <probe> is an id from tests/data/jq-error-probes.tsv. Columns are
# whitespace-separated; `#` lines and blank lines are ignored.
#
# The check is two-sided: a probe diverging without a line here fails the
# build, and a line here for a probe that now matches also fails the build — so
# every fix is forced to shrink this file, and no divergence can hide. The
# captured messages in tests/data/jq-error-messages.tsv always hold the correct
# (pinned jq) wording; only this manifest records where succinctly disagrees.
#
# Every entry must also have a section in docs/compliance/jq/limitations.md.
# See tests/data/jq-golden-known-failures.txt for the sibling manifest.
#
# Seeded from the #356 sweep: 102 of 102 probes diverged at the start; 96 were
# wording and were fixed there. Six were not, and two of those — `contains` and
# `inside` on operands whose kinds differ — were fixed by #358 before this file
# landed, so they never reached it. What remains below is not wording either —
# succinctly produces a value where jq errors, or cannot parse the filter — so
# each is a behaviour or parser bug with its own issue. (#359 fixed
# `setpath_on_number`, took the rest of `setpath`'s probes with it, and added
# the two slice probes it could not fix. #360 took the three `index_*_key_on_*`
# parser entries, which now reach the runtime error jq raises. #366 made a
# slice a real path component and took the last two, `slice_assign_non_array`
# and `slice_indices_not_integers`, emptying the list.)
#
# The list was empty, and the two-sided check kept it honest in both
# directions: a probe that starts diverging without a line here fails the
# build, so this file staying empty was an assertion, not an absence.
#
# This file cannot record the mirror image — a filter jq answers with a value
# and succinctly refuses — because a probe is only admitted if jq errors on it.
# Those live in prose, under "Where succinctly errors and jq does not" in
# docs/compliance/jq/limitations.md.
#
# Reseeded by #513 from the open bug corpus: two probes pinning bugs filed
# before a fix existed.
#
# #486 (`set_path`/`get_path_mut`/`update_path` now auto-vivify and pad the
# way `set_value_at_path` already did for `setpath()`) and #498 (the write-time
# negative-index bounds check now survives `?`, since `?` only ever suppressed
# errors raised while *collecting* a path) landed together and took
# `optional_write_negative_oob` with them: `.[-5]? = 9` now raises, matching jq.
#
# #530 fixed `path()`'s half of this — a filter that is not a path expression
# at all now raises jq's "Invalid path expression with result <v>" by name
# instead of silently answering with nothing — and took the three
# `path_non_path_*` probes below with it.
#
# The write side (`=`, `|=`, `del()`) still uses its own invented wording
# (`cannot use expression as {assignment,update,delete} target`) where jq
# raises that same sentence, because `set_path`/`delete_at_path` are not
# generic over the evaluator yet (unlike `update_path`) — aligning them needs
# a bigger refactor than #530's scope, so it is deferred to a follow-up issue
# and tracked here in the meantime.

assign_non_path_target               assign          `.a + 1 = 5` says "cannot use expression as assignment target" where jq says "Invalid path expression with result 2" — follow-up to #530
update_non_path_target               update          same, through `|=` — follow-up to #530
del_non_path_target                  del             same, through `del()` — follow-up to #530
assign_non_path_builtin              assign          same, through a builtin target (`length = 5`) — follow-up to #530
